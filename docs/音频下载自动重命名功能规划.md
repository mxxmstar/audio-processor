# 音频下载自动识别与重命名功能规划

> 状态：待实现
> 编制日期：2026-08-24
> 目标：音频下载完成后调用现有识别链路，根据艺术家和曲目标题自动生成文件名。

## 1. 背景与现状

当前项目已经具备下载和识别两条独立链路：

- B 站下载流程位于 `src-tauri/src/biliapi/task.rs` 和 `src-tauri/src/commands/bili.rs`。
- `AudioOnly` 当前按 B 站标题保存为 `<标题>.m4a`，首期目标改为转码后保存为 `.mp3`。
- 识别流程位于 `src-tauri/src/recognizer/`，顺序为 `fpcalc` → AcoustID → MusicBrainz。
- `recognizer::run_identify` 返回 `title`、`artist`、`album`、`album_date`、`confidence`。
- 下载和识别历史共用 `history.db`，下载历史的 `file_path` 当前由 `DownloadTask::output_file()` 推算。
- 下载进度通过 `download-progress` 事件推送，结束通过 `download-finished` 事件通知。

缺少的连接点是：下载完成后没有把实际音频文件交给 `run_identify`，也没有根据识别结果更新文件路径和历史记录。

## 2. 功能范围

### 2.1 首期目标

1. 仅对 `AudioOnly` 下载开启自动识别重命名。
2. 音频完整下载并关闭文件后再调用识别。
3. 默认生成 `曲目标题-艺术家.mp3`。
4. 文件名冲突时追加 ` (1)`、` (2)`，禁止覆盖已有文件。
5. 无匹配、低置信度、识别服务失败或重命名失败时，保留文件并使用 B 站原始标题兜底。
6. 下载历史保存实际最终路径、原始标题、识别结果和识别状态。
7. 批量任务独立处理，单个任务失败不影响其他任务。

### 2.2 首期不包含

- `VideoOnly` 和 `Merge` 模式的自动识别。
- 修改 MP3/MP4 内部标签，只修改文件名。
- 扫描并修复已有目录中的文件。
- 本地离线识别或大模型识别。
- 应用重启后自动扫描孤立临时文件。该能力作为后续增强。

## 3. 推荐产品行为

### 3.1 开关和阈值

- 下载界面增加“下载完成后自动识别并重命名”开关。
- 仅音频模式显示或生效，首期默认开启。
- 默认置信度阈值为 `70.0%`，作为配置传入后端，不能写死在命名函数中。
- 视频和合并模式忽略该开关，不触发首期自动识别。

### 3.2 命名规则

默认模板为 `{title}-{artist}`，最终统一输出为 MP3：

| 条件 | 结果 |
|---|---|
| 艺术家和标题有效且达到阈值 | `Song-Artist.mp3` |
| 艺术家缺失 | `Song.mp3` |
| 标题缺失 | 使用 B 站原始标题 |
| 无匹配或置信度不足 | 使用 B 站原始标题 |
| 同名文件存在 | 追加序号，不覆盖原文件 |

专辑信息首期保存到任务详情和历史记录，不默认拼进文件名。后续可支持 `{title}-{artist}-{album}` 等模板。

### 3.3 文件名清理

后端统一清理文件名，不能只依赖前端校验：

- 替换 Windows 非法字符 `\\ / : * ? " < > |`。
- 删除控制字符、首尾空格和首尾句点，合并连续空白。
- 处理 `CON`、`PRN`、`AUX`、`NUL`、`COM1`、`LPT1` 等保留名称。
- 限制文件名长度并保留扩展名空间。
- 清理后为空时使用 `未命名音频`。

## 4. 处理流程

```text
开始 AudioOnly 下载
    ↓
写入稳定的 .part 临时文件，保留断点续传能力
    ↓
下载完成，关闭文件并检查存在性/大小
    ↓
自动重命名关闭？──是──> 按 B 站标题落盘
    │
    否
    ↓
调用 recognizer::run_identify
    ↓
结果有效且达到阈值？──否──> 按 B 站标题兜底落盘
    │
    是
    ↓
清理“曲目标题-艺术家”，分配不冲突的目标路径
    ↓
同一输出目录内原子移动，更新任务、历史和前端事件
```

只有完整下载才允许进入识别。暂停时保留 `.part`，停止时删除 `.part`；识别失败不能删除已经下载的音频。

## 5. 后端设计

### 5.1 模块职责

建议新增纯本地模块 `src-tauri/src/audio_rename.rs`：

- `recognizer`：读取音频并返回 `SongInfo`，不关心下载任务和文件名。
- `audio_rename`：负责模板、清理、冲突处理和原子移动，不发网络请求。
- `biliapi::task`：编排下载完成后的识别和重命名时机。
- `commands::bili`：处理配置、任务状态、历史和 Tauri 事件。

后台任务直接调用 `recognizer::run_identify`，不要通过 `invoke` 嵌套调用 `identify` 命令。这样可以避免重复写识别历史和重复处理 Tauri 上下文。

### 5.2 配置模型

```rust
pub struct AutoRenameConfig {
    pub enabled: bool,
    pub confidence_threshold: f64,
    pub template: String,
}
```

默认值：`enabled = true`、`confidence_threshold = 70.0`、`template = "{title}-{artist}"`、`extension = "mp3"`。

`StartDownloadInput` 增加可选字段 `auto_rename` 和 `confidence_threshold`，使用 serde 默认值兼容旧版前端。

### 5.3 任务状态和路径

现有 `DownloadStatus` 只表示传输状态，不建议把“识别中”塞进该枚举。增加独立的 `RecognitionStatus`：

```rust
pub enum RecognitionStatus {
    Disabled, Pending, Recognizing, Renamed, NoMatch,
    BelowThreshold, Failed, RenameFailed,
}
```

`DownloadTask` 建议增加：

- `source_title`：B 站原始标题，永不被识别结果覆盖。
- `staged_path`：稳定的临时文件路径，用于续传和识别。
- `output_path`：实际最终落盘路径。
- `recognition_status`、`recognition_result`、`recognition_error`。

`output_path` 是历史记录和“打开文件”功能的唯一可信路径。`output_file()` 不能继续只根据当前标题推算，否则自动重命名后历史会指向旧路径。重命名完成后可以更新展示用 `title`，但必须保留 `source_title`。

### 5.4 临时文件

推荐路径格式：

```text
<output_dir>/.audio-processor-<task-key>.m4a.part
```

- `task-key` 由后端生成并清理，不能直接拼接原始 URL 或未经处理的标题。
- 同一任务每次继续下载必须得到相同路径，以保留 Range 断点续传。
- 临时文件放在最终输出目录内，确保最终移动在同一文件系统中完成。
- 下载完成后关闭文件句柄，再运行 `fpcalc`。
- 识别失败时将临时文件移动到兜底文件；兜底移动也失败时保留错误和临时路径，不能静默删除。

### 5.5 命名、冲突和并发

`audio_rename` 可提供以下纯本地函数：

```text
build_candidate_name(song_info, source_title, extension, config)
sanitize_filename_component(name)
allocate_unique_path(directory, candidate)
rename_atomically(source, destination)
```

规则：清理候选名、检查冲突、追加序号、禁止覆盖、源目标相同则直接成功。批量任务并发重命名时使用目录级锁或等价的无覆盖分配机制，避免两个任务同时选中同一个序号。

### 5.6 识别并发

下载并发度沿用当前配置，识别阶段使用独立 `Semaphore`，默认并发数为 `1`。必要时在 AcoustID/MusicBrainz 请求之间增加最小间隔，避免批量任务触发服务限流。一个任务识别失败不应取消其他任务。

现有 `run_identify` 中 MusicBrainz 补充失败不会丢弃 AcoustID 主结果，该行为应保留；只要艺术家和标题有效，就可以继续按阈值判断是否重命名。

### 5.7 fpcalc 路径

当前 `commands::identify` 按“打包资源目录 → 开发期仓库 `bin/`”查找 `fpcalc.exe`。自动重命名必须复用同一套路径解析函数，不能复制另一套规则。找不到 `fpcalc.exe` 时，文件仍按 B 站标题兜底并记录识别失败。

## 6. Tauri 命令、事件和历史

### 6.1 命令参数

扩展 `bili_start_download`：

```text
autoRename          是否启用自动识别重命名
confidenceThreshold 置信度阈值，可选
```

后端最终以任务模式和配置共同判断，只有 `AudioOnly && auto_rename == true` 才进入识别阶段。

### 6.2 进度事件

保留 `download-progress`，扩展 `phase`：`resolve`、`download`、`recognize`、`rename`。识别/重命名阶段至少发送 `task_id`、`phase`、`status`、`source_title`、当前标题、可选 `confidence`、`output_path` 和 `error`。

`download-finished` 建议增加 `renamed`、`recognize_failed`、`fallback` 统计。`ok` 继续表示下载传输是否全部成功；识别失败只进入统计，不把可用的已下载文件误报为下载失败。

### 6.3 历史记录

下载历史仍在批处理结束后写入，但必须使用最终任务快照：

```text
kind       = download
title      = 最终文件基础名
subtitle   = 下载模式 · 下载状态 · 识别状态
payload    = 包含 source_title、recognition_result、路径和错误的任务 JSON
file_path  = 实际最终文件路径
```

新增字段优先放入 JSON payload，避免首期频繁修改 SQLite 表结构。旧历史记录缺少新字段时使用默认值展示。

## 7. 前端改造

`src/DownloadView.vue` 需要：

- 增加自动重命名开关和可选阈值设置。
- 仅音频模式启用该开关，其他模式明确显示为不适用或隐藏。
- 任务列表展示“识别中”“已重命名”“未匹配”“识别失败”“使用原始标题”等状态。
- 下载传输结束后继续显示识别阶段，直到后处理完成。
- 任务详情展示原始标题、识别标题/艺术家、置信度、最终文件路径和错误原因。
- 后续增加“重试识别”按钮；重试应直接使用已落盘文件，不重新下载。

`src/HistoryView.vue` 的下载详情展示原始标题、最终文件名、识别状态、置信度和实际路径。“打开文件”始终使用 `file_path`，不能重新按标题拼接。

## 8. 实施阶段

### 阶段 1：纯本地命名能力

- 新增配置、命名模板、非法字符清理、保留名称处理和长度限制。
- 实现冲突编号、不覆盖已有文件、同目录原子移动和失败回退。
- 为中文/日文、特殊符号、长标题、空字段和同名文件补充单元测试。

完成标志：固定 `SongInfo` 和源文件可以得到稳定、不覆盖文件的目标路径。

### 阶段 2：接入下载和识别

- 扩展 `DownloadTask`、`BiliState` 和任务快照。
- AudioOnly 下载目标改为稳定 `.part` 文件。
- 完整下载后调用 `run_identify`，按阈值重命名或按原始标题兜底。
- 保持暂停、停止和 Range 续传语义。
- 识别失败不会删除文件，也不会阻塞其他任务。

完成标志：单个音频任务可以完成“下载 → 识别 → 重命名/兜底”。

### 阶段 3：事件、历史和界面

- 扩展任务序列化结构和进度事件。
- 更新任务列表、下载结束汇总和历史详情。
- 增加自动重命名开关与阈值配置。
- 实现识别失败提示；重试识别命令可作为本阶段末尾或下一阶段功能。

### 阶段 4：恢复和增强

- 提供孤立 `.part` 文件恢复/清理。
- 持久化未完成任务，支持重启后继续识别。
- 支持更多命名模板和专辑字段。
- 评估 Merge 模式识别合并后音频，以及独立的音频元数据写入功能。

## 9. 测试计划

### 9.1 单元测试

- 正常命名、艺术家/标题为空、低置信度和识别失败回退。
- 非法字符、控制字符、首尾空格/句点、Windows 保留名称和超长标题。
- 同名文件生成 `(1)`、`(2)` 且不覆盖原文件。
- 源目标相同不重复移动，重命名失败映射到正确状态。

### 9.2 下载编排测试

- `.part` 文件关闭后才开始识别。
- 暂停不触发识别，继续后完整下载只触发一次。
- 停止删除临时文件，VideoOnly/Merge 不触发首期识别。
- 自动重命名关闭时不调用识别模块。
- 一个任务识别失败时其他并发任务仍完成。
- 使用 mock 识别结果测试不同置信度和冲突场景。

### 9.3 构建和手工验收

- 本地假下载服务验证落盘和 Range 续传。
- Windows 打包环境验证 `fpcalc.exe` 资源路径。
- 使用真实短音频手工验证 AcoustID、MusicBrainz 和最终文件名。
- 运行 `cargo test`、`cargo build`、`npm run build`。

识别网络接口不应成为普通单元测试依赖。命名层应接收可注入的识别结果，真实服务链路只作为受控的集成或手工测试。

## 10. 风险与验收标准

| 风险 | 应对 |
|---|---|
| AcoustID 无匹配 | 使用 B 站标题兜底并记录 `NoMatch` |
| 识别结果错误 | 置信度阈值、保留原始标题和识别详情 |
| MusicBrainz 限流 | 识别并发默认为 1，并增加请求间隔 |
| 目标文件存在 | 追加序号，禁止覆盖 |
| 文件名非法或过长 | 后端统一清理和截断 |
| 应用崩溃留下临时文件 | 使用稳定 `.part` 路径，后续增加恢复/清理 |
| fpcalc 缺失 | 复用资源路径查找，按原始标题兜底 |

验收条件：

- [ ] 仅音频下载完成后自动进入识别。
- [ ] 达到阈值时生成 `曲目标题-艺术家.mp3`。
- [ ] 同名文件不被覆盖，识别失败仍保留可用音频。
- [ ] 下载状态和识别状态分别展示。
- [ ] 历史记录保存实际最终路径。
- [ ] 批量任务单个失败不阻塞其他任务。
- [ ] 暂停、停止、断点续传行为保持一致。
- [ ] `cargo test`、`cargo build`、`npm run build` 通过，且单元测试不依赖外网。

## 11. 建议实现顺序

先实现纯本地命名和冲突处理，再接入下载任务和识别链路，最后补事件、历史和界面。这样可以先验证文件移动、回退和不覆盖逻辑，再处理网络识别服务的不确定性。
