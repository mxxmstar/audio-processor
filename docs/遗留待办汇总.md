## A · 打包资源策略（AI 音质提升 / 音质优化）

### A.1 现状

**安装包实际打包的内容极少** —— `src-tauri/tauri.conf.json`：

```jsonc
"bundle": {
  "active": true,
  "targets": ["msi", "nsis"],
  // tauri.conf.json:40-42
  "resources": { "../bin/fpcalc.exe": "fpcalc.exe" }
}
```

只打了一个 `fpcalc.exe`。而 AI 后端运行依赖以下**全部未被打包**的东西：

| 依赖 | 运行时按什么路径解析 | 证据 |
|---|---|---|
| Worker 脚本 | `SCRIPT_ROOT = Path(__file__).resolve().parents[2]` → **项目根目录** | `python/audio_ai/worker.py:59`、`python/audio_ai_hifigan/protocol.py:25`、`python/audio_ai_flashsr/protocol.py:25` |
| 模型权重 / manifest | 同上（`SCRIPT_ROOT / "models"`） | `python/audio_ai_flashsr/selfcheck.py:20` |
| ffmpeg / ffprobe | 环境变量 → **仓库 `bin/`** → PATH | `python/audio_ai_hifigan/protocol.py:124-135`（`SCRIPT_ROOT / "bin"`） |
| Python 运行时 | `CARGO_MANIFEST_DIR/..` 下的 `.venv` / `.venv-flashsr`，再回退 `python` | `src-tauri/src/audio_quality/ai_worker.rs:847-877` |
| vendor 模型代码 | `ZipInstall/Model/Dataset/*`（Python 三方包，非本仓库代码） | 见各 Worker 说明 |

补充：
- 本机 `bin/` 现有 `ffmpeg.exe`、`ffprobe.exe`、`fpcalc.exe`、`aria2/`。
- `src-tauri/src/lib.rs:41-46` 在 setup 阶段计算 `ffmpeg_dir` 并 `set_ffmpeg_dir`，走的同样是开发环境的路径回溯。
- 规划文档已明确此为「后续必须完成的工作，不能把开发机的 `CARGO_MANIFEST_DIR` 路径视为生产路径」：
  `docs/低质量音频转高品质音频功能规划.md`（§第 16 节末，约 1080-1083 行）。

### A.2 问题（为什么打包版跑不了）

1. Worker 脚本 / Python 不在安装包里，`WorkerSpec` 找不到 `.venv*` 时回退到 `python`，
   而用户机器未必有 Python，更不会有 torch 等依赖。
2. Worker 脚本内的 `SCRIPT_ROOT = parents[2]` 依赖目录层级；一旦被打包到
   `resources/` 下扁平化，路径语义就失效（`bin/`、`models/` 都找不到）。
3. **权重体量决定不能随包分发**（见下表），必须是「包内带脚本 + 运行时下载」。

| 模型 | 体积（来自 `models/manifest.json`） |
|---|---|
| `flashsr`（student_ldm + sr_vocoder + vae） | 1033200174 + 627861067 + 1655458345 ≈ **3.3 GB** |
| `audiosr-basic` | 6178189567 ≈ **6.2 GB** |
| `deepfilternet2-speech` | 小（约 20 MB 级 zip） |
| `hifigan-48k`（22.05k jik876） | 约百 MB 级，**尚未取到本地**（构建环境不可达，见 HiFi-GAN 计划 §4.6） |

### A.3 待办项分解

| 编号 | 待办 | 说明 |
|---|---|---|
| A1 | **定 Python 运行时分发方案** | 三选一：① 随包嵌入精简 venv（包体巨大）② 首次启动引导装依赖到用户目录 ③ 打包独立 Python 便携版。需先拍板 |
| A2 | Worker 脚本改为**资源相对定位** | `SCRIPT_ROOT` 不能再依赖 `parents[2]`；改为读 Rust 侧注入的绝对路径（环境变量 `AUDIO_AI_*`），或按 `resource_dir()` 解析 |
| A3 | 把脚本 + ffmpeg/ffprobe 声明进 `bundle.resources` | 含 `bin/ffmpeg.exe` 及其依赖 DLL（历史教训：`开发计划.md:272-275` 记载过动态链接版 ffmpeg 缺 DLL 导致 `0xC0000135`） |
| A4 | **模型权重走运行时下载** | 复用现有 `audio_quality_download_model` → `model_manager`（已支持 HTTPS + 断点续传 + SHA-256；新增的 `deferred` 延迟校验用于体积未知的条目） |
| A5 | 打包后冒烟清单 | 见 A.5 |

### A.4 建议要点

- A2 是 A 里最该先解耦的：**把「路径解析」从 Python 侧上移到 Rust 侧**，由 Rust 通过环境变量
  把 `resource_dir` 传给 Worker，Python 不再猜 `parents[2]`。这与现有 `AUDIO_AI_MODEL_DIR`、
  `AUDIO_AI_FFMPEG` 的注入方式一致，改动可控。
- A4 已经具备基础设施（`model_manager`），主要工作是 UI/首次启动引导，而非重做下载器。
- 建议 A1 单独出方案文档并确认后再动工。

### A.5 验收标准

- [ ] `npm run tauri build` 产出的安装包，在**没有 Python、没有 Rust 工具链、没有仓库源码**的干净机器上安装后，
      打开「音质提升 / 音质优化」能正常检出「运行时已连接」（或给出明确的安装引导文案）。
- [ ] 在该机器上点「安装模型」可完成下载校验，并跑通一次真实推理（对应
      `hifigan_real_worker_forward_pass` / FlashSR 真实前向）。
- [ ] 干净机器上 `ffmpeg` 可用（音视频合并、AI 后端解码/编码均不报 `STATUS_DLL_NOT_FOUND`）。
- [ ] 不存在任何依赖 `CARGO_MANIFEST_DIR` 或仓库源码目录的生产路径。

### B1 · 会员限制 / 风控错误的可读化文案

**现状**：`src-tauri/src/biliapi/error.rs:13-14`

```rust
#[error("B 站接口返回错误码 code={code}, message={message}")]
Api { code: i64, message: String },
```

所有 B 站业务错误都直出「`B 站接口返回错误码 code=-404, message=啥都木有`」，
用户看到的是原始错误码。常见需映射的码：

| code | 典型含义 | 建议文案 |
|---|---|---|
| `-404` | 稿件不存在 / 需要会员或地区限制 | 「该视频不存在，或需要大会员 / 受地区限制」 |
| `-412` | 请求被拦截（风控） | 「请求被 B 站风控拦截，请稍后重试或登录后重试」 |

**期望**：在 `error.rs` 增加错误码 → 友好文案的映射（保留原始 `code/message` 供排查，
可以拼接在末尾或写入日志），前端 `invoke` 失败时直接展示友好文案。

**涉及文件**：`src-tauri/src/biliapi/error.rs`（主要）、可能涉及调用方展示。

**验收**：登录后解析一个大会员专用视频，UI 报出可读文案而非 `code=-404`；
正常/其他错误码行为不变；`cargo test --lib` 全绿。

### B2 · `ep` 单链接走番剧 `resolve_season` 路径

**现状**：`src-tauri/src/commands/bili.rs:951-964`（`identify()`）

```rust
if let Some(ep) = extract_query(s, "ep_id")
    .or_else(|| extract_path_token(s, "ep").or_else(|| extract_prefixed_token(s, "ep")))
{
    // ep 也需要 season 信息，但 resolve_season 仅接受 ssid；
    // 简化：ep 直接当作 ss 不可用，这里回退用 bvid 解析
    if let Some(bvid) = extract_query(s, "bvid") { return Target::Bv(bvid); }
    if let Some(bvid) = extract_bvid_from_url(s) { return Target::Bv(bvid); }
    // 退化为 Season（ssid 缺失时由 video 层报错）
    return Target::Season(ep);
}
```

即 **`ep` 链接不会走番剧解析**：能抠出 bvid 就退化成单集 BV 解析（丢失整季）；
抠不出就 `Target::Season(ep)` 把 ep 当 ssid 用，最终在 video 层报错。

关键点：底层**已经支持**按 `ep_id` 取番剧信息 ——

- `src-tauri/src/biliapi/video.rs:40-45` `get_season_info(client, epid, ssid)`：
  `(Some(ep), _) => cfg.query("ep_id", ep)`、`(_, Some(ss)) => cfg.query("season_id", ss)`；
- 但 `src-tauri/src/biliapi/video.rs:418` `resolve_season(client, ssid, ...)` **只接受 ssid**；
- `Target::Season(String)` 语义也是存 ssid（`bili.rs:914`）。

**修复方案已验证可行**：`SeasonInfo` 带 `season_id` 字段（`src-tauri/src/biliapi/types.rs:263`），
因此可以在**异步**解析前把 `ep_id` 换成 `season_id`：

1. `identify()` 识别到 `ep` 时返回新分支（如 `Target::Ep(ep_id)`），避免在纯函数里发请求；
2. 在真正发起解析（`bili_resolve` 的命令体，`bili.rs:236-293` / `459`）之前，
   先 `video::get_season_info(&client, Some(ep_id), None)`（参数序为 `(client, epid, ssid)`，
   用法参考 `bili.rs:348` 的 `get_season_info(&client, None, Some(ssid))`），
   取 `SeasonInfo.season_id`，再走既有的 `Target::Season(ssid)` 路径。

> 之所以不能直接在 `identify()` 里做：`identify()` 是同步纯函数且被调用多次
> （`bili.rs:234` 与 `338` 各一次），不适合塞网络请求。

**涉及文件**：`src-tauri/src/commands/bili.rs`（`Target` 枚举 908-915、`identify` 918-977、
解析命令体 236-293 / 340-460）；`src-tauri/src/biliapi/types.rs:261-275`（`SeasonInfo`，无需改动）。

**风险/注意**：需实际抓一条番剧 `ep` 链接验证 B 站返回的 `SeasonInfo` 能拿到 `season_id`，
且注意 `resolve_season` 的并发/回调不改坏（`video.rs:418-482`）。

**验收**：输入 `https://www.bilibili.com/bangumi/play/ep123456` 能列出整季分集并可选集下载；
输入 ss 链接行为不变。
