# 低质量音频转高品质音频功能规划

> 状态：实施中（AudioSR 通用音乐恢复适配和下载集成已完成，独立页面与正式音质验收待完成）
> 编制日期：2026-08-24
> 目标：先实现一个可独立使用、可验证、不会破坏原文件的音频质量处理模块，再接入下载完成后的后处理流程。

## 1. 先明确“提升音质”的边界

低码率 MP3、AAC 等有损音频已经丢失了部分原始信息。把它重新编码为 320 kbps MP3、FLAC 或更高采样率，不会恢复这些细节，只会生成一个规格更高但信息量未增加的文件。因此产品和任务状态不能把普通转码显示为“无损恢复”。

本功能需要区分以下几类操作：

| 类型 | 能做什么 | 是否恢复丢失细节 | 首期建议 |
|---|---|---:|---|
| 无损重封装 | 在容器之间迁移音频流，不重新编码 | 否，但不引入二次损失 | 支持 |
| 普通转码 | 改变编码器、格式、码率或采样率 | 否，可能再次损失 | 支持 |
| 音频处理 | 音量标准化、限幅、轻度去噪、去削波等 | 改善部分听感，不保证恢复 | 谨慎支持 |
| AI 修复/超分 | 预测高频、去噪、去混响、去削波 | 只能估计，不保证真实还原 | 后续独立后端 |

首期产品名称建议使用“音频质量处理”或“音频增强”，并在详情中显示实际处理方式，例如“转码为 MP3 320 kbps”“已进行响度标准化”。对于有损输入，不显示“已恢复无损音质”。

## 2. 当前项目基础

项目已有可以复用的基础：

- `src-tauri/src/biliapi/media.rs` 已负责 FFmpeg 探测和进程调用。
- `media::transcode_audio` 已能将下载的音频转为 MP3，但参数固定为 `libmp3lame + -q:a 2`，不能表达完整的质量处理配置。
- `src-tauri/src/recognizer/` 已是与 Tauri 解耦的独立音频识别模块，可作为模块拆分和错误处理的参考。
- `src-tauri/src/biliapi/task.rs` 已有下载任务、临时文件和最终路径的概念。
- 前端使用 Vue 视图、Tauri command 和事件回传，适合新增独立的处理页面。

本功能不应直接扩大 `recognizer` 的职责。识别负责回答“这是什么音频”，质量处理负责回答“如何生成目标音频文件”，两者使用路径和结果交接即可。

## 3. 功能目标与非目标

### 3.1 首期目标

1. 选择一个或多个本地音频文件进行处理。
2. 处理前读取并展示输入音频的真实参数：格式、编码器、码率、采样率、声道、位深、时长和响度概况。
3. 提供明确的输出配置：输出格式、编码器、码率或质量、采样率、声道和响度处理。
4. 使用 FFmpeg 执行处理，支持进度、取消、失败状态和批量任务。
5. 输入文件默认不覆盖；输出写入同目录或用户指定目录的临时文件，成功校验后再原子移动。
6. 处理失败时保留原文件和错误信息，不能因为输出失败删除输入文件。
7. 对输出文件进行基本可播放性和参数校验，并记录实际使用的 FFmpeg 命令配置。
8. 为后续 AI 修复保留后端接口，但首期不捆绑大型模型或远程服务。

### 3.2 首期不包含

- 声称将 64/128 kbps 有损音频恢复为真正的 CD 级或母带级音质。
- 直接覆盖原文件。
- 首期内置 AI 模型下载、模型管理和 GPU 推理。
- 对视频文件做音轨替换或视频重新封装。
- 自动批量修改文件名和内部标签；命名仍由现有自动识别重命名流程负责。
- 以主观听感作为唯一验收标准。

## 4. 推荐处理档位

首期使用用户容易理解、但技术含义准确的档位。高级参数可以在“自定义”中展开。

### 4.1 保持源质量

适用于只需要转换容器或保留原编码的场景：

- 优先使用 `-c:a copy`，不重新编码。
- 当目标容器不兼容源编码时，明确提示会发生转码。
- 输出格式默认与源格式相容，不因为文件扩展名强行改变编码。

该档位不适合把低码率音频“变高质量”，但可以避免再次压缩。

### 4.2 高质量 MP3

适用于需要兼容性较好的 MP3 输出：

- 编码器：`libmp3lame`。
- 默认质量：VBR `-q:a 2`，与当前下载流程的默认行为保持一致。
- 可选固定码率：128、192、256、320 kbps。
- 默认不升采样；输出采样率跟随源文件，只有用户明确选择时才转换。

需要在界面上说明：选择 320 kbps 会得到高规格 MP3，不会恢复输入文件已经丢失的音频细节。

### 4.3 无损格式输出

适用于源文件本身为 WAV、FLAC、ALAC 等无损格式，或用户明确需要统一归档格式：

- 默认输出 FLAC。
- 源文件为有损格式时，显示“有损转 FLAC，仅改变容器/编码，不增加源文件信息量”的提示。
- 不把有损转 FLAC 的文件标记为“恢复无损”。

### 4.4 轻度音频处理

在自定义模式中按开关启用，并在任务详情中记录滤镜：

- 响度标准化：优先使用 `loudnorm`，显示目标 LUFS 和 true peak。
- 限幅：避免处理后峰值削波，必要时使用 `alimiter`。
- 轻度去噪：可评估 FFmpeg `afftdn`，默认关闭，避免音乐细节被误删。
- 去削波：可评估 `adeclip`，默认关闭，处理前后必须检查峰值和波形结果。
- 采样率转换：使用高质量 `soxr`，但不把升采样描述为增加频率细节。

首期不要默认串联过多滤镜。每增加一个滤镜，都应提供可回退的原文件、记录参数，并使用有代表性的音频样本进行听感和指标对比。

## 5. 独立模块设计

建议新增 `src-tauri/src/audio_quality/`，模块职责类似 `recognizer`，但只处理本地文件和 FFmpeg，不依赖 B 站任务。

### 5.1 推荐目录

```text
src-tauri/src/audio_quality/
├── mod.rs       对外 API、处理流程和类型导出
├── probe.rs     音频参数探测，优先使用 ffprobe
├── profile.rs   质量档位和输出配置
├── processor.rs FFmpeg 参数构造、启动、进度解析和结果校验
└── error.rs     可序列化的错误类型
```

若暂时没有 `ffprobe.exe`，可以先通过 FFmpeg 探测或限制首期展示字段；但建议随 `ffmpeg.exe` 一起提供匹配版本的 `ffprobe.exe`。不要通过解析人类可读的 FFmpeg 文本来作为长期数据接口，应优先使用 `ffprobe -of json`。

### 5.2 核心数据结构

建议使用稳定的 Rust 类型，Tauri 层只负责参数转换和事件转发：

```rust
pub struct AudioProbe {
    pub path: String,
    pub format: String,
    pub codec: String,
    pub duration_seconds: f64,
    pub bitrate: Option<u64>,
    pub sample_rate: Option<u32>,
    pub channels: Option<u16>,
    pub bit_depth: Option<u16>,
    pub lossless: bool,
    pub loudness: Option<LoudnessInfo>,
}

pub struct AudioQualityConfig {
    pub profile: QualityProfile,
    pub output_format: OutputFormat,
    pub bitrate_kbps: Option<u32>,
    pub sample_rate: Option<u32>,
    pub channels: ChannelMode,
    pub loudness: Option<LoudnessConfig>,
    pub denoise: bool,
    pub overwrite: bool,
}

pub enum ProcessingStatus {
    Pending,
    Probing,
    Processing,
    Verifying,
    Completed,
    Failed,
    Cancelled,
}

pub struct AudioProcessTask {
    pub id: String,
    pub input_path: String,
    pub output_path: Option<String>,
    pub input_probe: Option<AudioProbe>,
    pub output_probe: Option<AudioProbe>,
    pub config: AudioQualityConfig,
    pub status: ProcessingStatus,
    pub progress: f64,
    pub error: Option<String>,
}
```

实际实现可以按项目现有序列化方式调整，但应保留 `input_path`、`output_path`、输入/输出探测结果和配置快照，方便历史记录和问题排查。

### 5.3 对外 API

核心模块建议提供以下能力：

```text
probe(path) -> AudioProbe
validate_config(probe, config) -> Result<ValidatedConfig>
process(input, output, config, cancel, progress) -> Result<ProcessResult>
verify(output, expected_config) -> Result<AudioProbe>
```

`process` 不应负责选择文件、写历史或触发 Tauri command。它只接收输入路径、已分配的输出路径、配置和回调。这样可以在单元测试中使用 mock FFmpeg，也能在未来从下载任务直接调用，而不需要嵌套 `invoke`。

## 6. FFmpeg 执行与文件安全

### 6.1 处理流水线

```text
选择输入文件
    ↓
探测输入参数
    ↓
校验配置与输入兼容性
    ↓
在目标目录创建唯一的 .audio-processor-*.part
    ↓
启动 FFmpeg，解析进度并支持取消
    ↓
检查退出码、文件存在性、文件大小和输出参数
    ↓
原子移动到最终路径，写入任务/历史
```

FFmpeg 必须通过参数数组调用，不拼接 shell 字符串。输入、输出路径使用 `-i` 和最终参数传递，避免路径中空格、中文或特殊字符导致命令注入和解析错误。

### 6.2 临时文件和覆盖策略

- 临时文件与最终输出放在同一目录，尽可能保证移动是同一文件系统内的原子操作。
- 临时文件使用任务 ID，不使用未经清理的原始文件名。
- 默认不覆盖已存在的目标文件；同名时追加 `(1)`、`(2)`，复用现有 `audio_rename` 的冲突分配规则。
- 只有用户显式选择覆盖时才传递 `-y`，且仍先写临时文件，不能让 FFmpeg 直接破坏原目标。
- 成功移动后才删除临时文件和可选的原始文件；首期默认保留原始文件。
- 取消或失败时清理当前任务的临时输出，不触碰输入文件。

### 6.3 FFmpeg 进度

使用 `-progress pipe:1 -nostats` 输出机器可读进度，结合输入时长计算百分比。需要处理：

- 输入没有时长或时长为零：进度显示为“不确定”，不能伪造百分比。
- FFmpeg 输出错误在 stderr 中读取并截取可读尾部，避免把整个日志塞进任务状态。
- 取消时终止子进程并等待退出，避免残留 FFmpeg 进程锁住临时文件。
- 进度回调节流，避免每行 FFmpeg 输出都触发前端事件。

现有 `media::find_ffmpeg` 的探测逻辑应提取为公共能力复用；如果增加 `ffprobe`，探测路径和版本匹配规则也应集中管理。

## 7. Tauri 后端与前端

### 7.1 Tauri commands

建议新增独立命令模块，例如 `src-tauri/src/commands/audio_quality.rs`：

| 命令 | 作用 |
|---|---|
| `audio_quality_probe` | 探测一个或多个文件并返回输入参数 |
| `audio_quality_start` | 创建处理任务并立即返回任务 ID |
| `audio_quality_list_tasks` | 返回当前任务快照 |
| `audio_quality_cancel` | 取消指定任务 |
| `audio_quality_open_output` | 可选，打开输出文件或所在目录 |
| `audio_quality_clear_tasks` | 清理已结束的任务记录 |

处理在后台执行，前端通过 `audio-quality-progress` 事件接收：

```text
task_id、phase、status、percent、input_path、output_path、speed、error
```

阶段至少包括 `probe`、`process`、`verify`、`completed`。下载的 `download-progress` 事件继续只表达下载流程，避免两个模块共享一套含义不一致的状态。

### 7.2 前端独立页面

建议新增 `AudioQualityView.vue`，首期工作流为：

1. 选择本地音频文件。
2. 展示输入质量信息和文件大小。
3. 选择质量档位或自定义配置。
4. 预览输出格式、预计文件大小范围和“是否可能二次有损编码”的提示。
5. 启动、暂停/取消处理。
6. 展示每个任务的处理阶段、进度、输出文件和错误。
7. 处理完成后提供打开文件或打开目录操作。

首期不需要设计复杂的音频编辑器，也不需要展示无法可靠计算的“音质提升百分比”。如果输入是有损文件，应展示客观参数变化和免责声明，而不是虚构质量评分。

### 7.3 配置持久化

默认档位、输出目录、最后一次码率和响度目标可以写入现有应用配置；单个任务仍保存完整配置快照。配置版本需要保留，未来增加字段时使用默认值兼容旧任务。

## 8. 独立模块实施阶段

### 阶段 1：探测和纯本地配置层

- 确认并统一 `ffmpeg.exe`、`ffprobe.exe` 的开发期和打包期路径。
- 新增 `AudioProbe`、质量档位、输出格式和配置校验。
- 实现输入格式、码率、采样率、声道、时长的 JSON 探测。
- 实现文件名冲突、扩展名和临时路径分配。
- 不启动 Tauri，不接下载流程，先用固定样本测试。

完成标志：同一输入在不同配置下能得到稳定、可解释的校验结果，错误参数不会启动 FFmpeg。

### 阶段 2：FFmpeg 处理核心

- 实现保持源质量、高质量 MP3、FLAC 输出三个基础档位。
- 实现 `-progress` 进度解析、取消和错误映射。
- 实现临时文件、输出验证和原子移动。
- 添加轻度响度标准化的可选实现；默认关闭去噪等可能改变音色的滤镜。
- 为每种输出保存实际配置和探测结果。

完成标志：输入文件始终保留，成功任务输出可播放且参数符合配置，失败任务无半成品冒充成功。

### 阶段 3：Tauri 命令和独立页面

- 注册 command 和 `audio-quality-progress` 事件。
- 新增任务状态管理和并发限制。
- 完成文件选择、参数设置、批量处理、取消、打开输出。
- 增加历史记录或至少提供任务详情导出，确保重启前能查到输出路径和错误。

完成标志：不经过 B 站下载页面，用户可以直接处理本地音频并完成端到端验收。

### 阶段 4：试听和质量评估

- 使用 WAV、FLAC、AAC、MP3 的固定样本覆盖无损和多种有损输入。
- 记录输入/输出 codec、码率、采样率、响度、true peak 和削波计数。
- 对去噪、限幅、响度标准化样本进行人工试听，记录误伤细节的情况。
- 建立“只改变格式”“改变音量”“改变频谱”的测试样本，避免把不同问题混在一起。

完成标志：每个档位都有清晰的收益、代价和适用输入，不以单一文件的听感作为普遍结论。

## 9. 与下载流程的集成阶段

独立模块稳定后，再接入 `AudioOnly` 下载。推荐集成顺序如下：

```text
下载到 .m4a.part
    ↓
关闭文件并检查完整性
    ├─ audioRecognitionEnabled = true
    │      ↓
    │  用原始下载文件执行音频识别
    │
    ├─ pythonAiEnhancementEnabled = true
    │      ↓
    │  启动 Python AI Worker 进行增强
    │      ↓
    │  校验 AI 输出
    │
    ├─ audioRecognitionEnabled = true
    │      ↓
    │  按识别结果分配最终文件名
    │
    └─ audioRecognitionEnabled = false
           ↓
       按 B 站原始标题或用户命名规则分配最终文件名
    ↓
更新任务状态、实际路径和下载历史
```

“原始音频识别”和“Python AI 增强”是两个互相独立的可选配置项，不允许一个开关隐式打开另一个开关。两项都开启时，识别仍应放在 AI 处理之前，因为 AI 可能改变频谱和指纹；仅开启 AI 时不执行识别，文件名直接使用 B 站原始标题或用户命名规则；仅开启识别时保持现有自动识别重命名流程；两项都关闭时只执行基础下载和目标格式转换，不调用识别服务和 Python Worker。

无论哪一项失败，都必须保留原始下载文件。识别失败只影响命名结果，AI 失败只影响增强结果，不能把后处理失败报告成下载失败，也不能让一个开关的失败阻塞另一个已启用的独立阶段。

### 9.1 下载配置扩展

在现有下载输入中增加两个独立的可选配置组：

```text
audioRecognitionEnabled         是否识别原始音频并自动重命名
recognitionConfidenceThreshold  识别置信度阈值
recognitionTemplate             文件名模板，默认 {title}-{artist}

pythonAiEnhancementEnabled      是否启动 Python AI Worker 增强
pythonAiModelId                 AI 模型 ID
pythonAiDevice                  auto / cpu / cuda
pythonAiChunkSeconds            AI 分块长度
pythonAiOverlapSeconds          AI 分块重叠长度
pythonAiOutputFormat            wav / flac / mp3
keepAiMaster                    是否保留 AI 生成的 WAV/FLAC
keepOriginalAudio               是否保留原始下载文件，默认 true
```

配置含义必须保持独立：

| 原始音频识别 | Python AI 增强 | 执行内容 | 命名来源 |
|---:|---:|---|---|
| 关 | 关 | 基础下载和目标格式转换 | B 站原始标题 |
| 开 | 关 | 原始音频识别、按结果重命名 | 识别结果，失败时回退原始标题 |
| 关 | 开 | Python AI 增强、输出校验和目标格式转换 | B 站原始标题 |
| 开 | 开 | 原始音频识别 → Python AI 增强 → 输出校验 → 目标格式转换 | 识别结果，失败时回退原始标题 |

旧版前端不传新增字段时，为保持当前自动重命名行为，后端可以将 `audioRecognitionEnabled` 兼容解析为旧字段 `autoRename`，默认按旧行为开启识别；`pythonAiEnhancementEnabled` 默认关闭。新前端必须显式发送两个开关，不能继续使用含义不清的单一 `audioQualityEnabled`。视频、仅视频和合并模式首期不进入这两个音频后处理阶段。

### 9.2 任务状态

不要把“处理中”直接覆盖下载传输状态。原始音频识别和 Python AI 增强也不能共用一个状态字段。应在现有 `DownloadTask` 中分别保存两类状态，例如：

```text
recognition_status       Disabled / Pending / Recognizing / Renamed /
                          NoMatch / BelowThreshold / Failed / RenameFailed
recognition_config       本次识别开关、阈值和文件名模板
recognition_result       标题、艺术家、置信度等识别结果
recognition_error        识别或命名错误
```

```text
quality_status        Disabled / Queued / CheckingRuntime / LoadingModel /
                      Processing / Encoding / Verifying / Completed /
                      Failed / Cancelled
quality_config       本次实际使用的配置
quality_input_path   处理输入路径
quality_output_path  处理输出路径
quality_probe        输入/输出参数摘要
quality_error        处理错误
```

未启用的功能状态必须是 `Disabled`，不能用 `Failed` 表示“用户没有选择该功能”。下载成功但某个后处理失败时，下载任务仍为 `Completed`，对应的识别或质量状态为 `Failed`，并将原始文件路径作为可操作输出。这样用户不会因为某个可选后处理失败而误以为下载内容丢失。

### 9.3 推荐的文件保留策略

默认保留原始音频：

```text
原始下载：<目录>/.audio-processor-<id>.m4a.part
处理临时：<目录>/.audio-processor-<id>.mp3.part
最终增强：<目录>/曲目标题-艺术家.mp3
原始归档：<目录>/曲目标题-艺术家.source.m4a
```

实际命名可以简化，但必须保证：

- 质量处理成功前不删除 `.m4a`。
- 用户选择保留原文件时，原文件必须有明确的 `.source` 或独立子目录。
- 不允许输出文件和输入文件路径相同后直接覆盖。
- 下载历史同时保存原始输入路径、处理输出路径和最终用户可见路径。

首期如果不想增加用户可见的原始副本，可以保留隐藏源文件并在任务详情中提供“保留原始文件”设置；无论 UI 如何呈现，失败回退路径必须存在。

## 10. AI 修复/超分的后续方案

AI 能力应作为 `audio_quality` 的另一种处理后端，而不是修改现有 FFmpeg 参数来冒充 AI：

```text
AudioQualityBackend
├── FfmpegBackend       转码、重采样、响度、轻度滤镜
└── AiEnhancementBackend 去噪、去混响、频带扩展、去削波
```

AI 后端需要单独解决：

- 模型文件体积、版本、许可证和校验值。
- CPU/GPU 推理能力探测和显存/内存占用。
- 长音频分段、重叠窗口、拼接边界和延迟。
- 输入输出采样率、声道和模型支持范围。
- 取消任务时安全终止推理，避免残留进程。
- 效果不可逆，必须保留源文件和增强前后对比试听能力。
- 不同音乐类型可能出现伪影，必须允许关闭和回退。

AI 后端完成前，产品只应提供“转码”“重采样”“响度处理”等准确描述。评估 AI 时，可以先以独立命令行原型验证样本效果，再决定是否将模型随应用分发。

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 高码率输出被误解为音质恢复 | UI 和任务详情显示真实处理类型，不使用“恢复无损”表述 |
| 再次有损编码造成更多损失 | 默认提供源流复制/FLAC 选项，明确提示二次编码 |
| 升采样只增加采样点 | 默认跟随源采样率，使用高质量重采样且不虚构收益 |
| 去噪/限幅损伤音乐细节 | 默认关闭高风险滤镜，逐项开关，保留原文件 |
| FFmpeg/ffprobe 版本或路径不一致 | 集中探测、启动时记录版本，打包时放入匹配资源 |
| 输出中途失败留下假成功文件 | `.part` + 退出码/参数/可播放性校验 + 原子移动 |
| 批量任务占满 CPU/磁盘 | 独立处理并发配置，默认并发 1 或 2，限制队列 |
| AI 模型产生伪影或资源占用过高 | AI 单独后端、可关闭、保留源文件并限制模型范围 |

## 15. 方案修订：Rust 启动 Python AI 子进程

### 15.1 修订结论

前文的 FFmpeg 方案只能完成格式转换、重采样、响度处理和有限的传统滤镜，不能满足“使用 AI 改善低质量音频”的目标。本项目的 AI 方案调整为：

```text
Tauri/Vue
    ↓ command / event
Rust 音频质量模块
    ↓ tokio::process::Command
Python AI Worker 子进程
    ↓
AI 模型推理（带宽扩展、去噪或去削波）
    ↓
输出无损中间文件（WAV/FLAC）
    ↓
Rust 校验并按用户要求编码为最终格式
```

职责边界：

| 组件 | 负责内容 | 不负责内容 |
|---|---|---|
| Vue/Tauri | 选择文件、配置模型、展示状态和错误 | 直接加载 Python 模型 |
| Rust | 任务队列、文件安全、启动/停止子进程、协议解析、进度、历史 | AI 张量计算和模型细节 |
| Python Worker | 解码、预处理、模型加载、分块推理、后处理、写出音频 | 下载任务、文件重命名和数据库历史 |
| FFmpeg/ffprobe | 格式探测、解码/编码、最终参数校验 | 判断 AI 效果是否真实提升 |

本节是对前文“AI 后端后续评估”的具体化，后续实施以本节为准。产品文案使用“AI 音频增强”或“AI 带宽扩展”，不使用“无损恢复”。AI 输出可能包含模型估计的高频和被重建的细节，必须允许用户保留原文件并进行试听对比。

### 15.2 为什么使用子进程

Python 的 AI 生态主要集中在 PyTorch、ONNX Runtime、torchaudio、numpy 和各类模型仓库中。将 Python 放在独立子进程中有几个实际好处：

- Rust 主进程不需要嵌入 Python，也不会被 Python 包版本和 GIL 绑住。
- Python 模型崩溃、CUDA 初始化失败或内存溢出时，可以隔离并报告为单个任务失败。
- AI 依赖和现有识别依赖可以分开管理，避免污染当前 `requirements.txt`。
- 后续更换模型或推理框架时，Rust 只需要保持协议兼容。
- 取消任务时可以结束整个 Worker 进程，避免模型继续占用 GPU 和文件句柄。

首期推荐“一个处理任务启动一个 Worker 进程”。这样生命周期和资源回收最容易验证。模型加载完成后，如果频繁启动导致体验或性能不可接受，再增加长驻 Worker 和任务复用；不要一开始就引入复杂的进程池。

### 15.3 Python Worker 目录和依赖隔离

当前仓库已有：

- `recognizer.py`：现有音频识别命令行脚本。
- `requirements.txt`：当前识别链路的 Python 依赖。

AI 不直接修改这两个文件的职责。建议新增独立目录：

```text
python/
└── audio_ai/
    ├── __main__.py          Worker 入口，只处理协议和退出码
    ├── protocol.py          JSONL 请求/事件结构
    ├── pipeline.py          解码、分块、模型推理、写出
    ├── backends.py          模型后端注册和版本信息
    └── probe.py              Python 侧输入/输出校验辅助
requirements-ai.txt         AI 专用依赖，不与识别依赖混用
models/
└── manifest.json            模型 ID、版本、文件名、SHA-256、许可信息
```

`requirements.txt` 继续服务识别脚本，`requirements-ai.txt` 独立锁定 AI 依赖。AI 依赖通常包含体积较大的 PyTorch/CUDA 包，不能默认在应用启动时联网安装，也不能让用户点击下载后静默改变运行环境。

Python Worker 的 stdout 只能输出协议 JSONL，日志全部写 stderr。这样 Rust 不会因为解析到 Python 的普通 `print` 文本而误判任务状态。现有 `recognizer.py` 的人类可读输出适合手工识别，不适合直接充当 AI Worker 协议。

### 15.4 Rust 与 Python 的通信协议

采用“一行一个 JSON 对象”的 JSONL 协议，使用 UTF-8。Rust 通过 stdin 发送请求，Python 通过 stdout 返回事件；stderr 只作为诊断日志。协议必须带版本和任务 ID，后续可以在不破坏旧 Worker 的前提下扩展字段。

请求示例：

```json
{"protocol_version":1,"request_id":"aq-001","command":"process","input_path":"E:/audio/source.m4a","output_path":"E:/audio/.audio-processor-aq-001.flac.part","model_id":"music-bandwidth-v1","device":"auto","chunk_seconds":20,"overlap_seconds":2,"output_sample_rate":48000}
```

Worker 启动后先发送就绪事件：

```json
{"protocol_version":1,"request_id":"aq-001","type":"ready","worker_version":"0.1.0","models":["music-bandwidth-v1"]}
```

处理过程中发送：

```json
{"protocol_version":1,"request_id":"aq-001","type":"progress","phase":"load_model","percent":12.0,"message":"正在加载模型"}
{"protocol_version":1,"request_id":"aq-001","type":"progress","phase":"inference","percent":58.5,"processed_seconds":143.2,"total_seconds":247.0}
```

成功和失败发送终结事件：

```json
{"protocol_version":1,"request_id":"aq-001","type":"result","status":"completed","output_path":"E:/audio/.audio-processor-aq-001.flac.part","model_id":"music-bandwidth-v1","model_version":"1.0.0","sample_rate":48000,"channels":2,"duration_seconds":247.02,"peak_db":-1.2}
```

```json
{"protocol_version":1,"request_id":"aq-001","type":"error","code":"OUT_OF_MEMORY","message":"AI 推理内存不足","retryable":false}
```

协议约束：

- stdout 每行必须是完整 JSON，Rust 对单行设置长度上限，防止异常日志耗尽内存。
- `result` 或 `error` 只能出现一次，终结事件之后忽略后续数据并记录协议错误。
- Rust 不信任 Python 返回的 `output_path`，最终路径以 Rust 创建和校验的路径为准。
- Python 不接收 shell 命令，只接收结构化路径和配置；Rust 使用 `Command` 参数数组启动进程。
- Rust 读取 stdout 和 stderr 必须并发进行，避免 Worker 因 stderr 缓冲区写满而死锁。
- 超时、协议版本不兼容、Worker 提前退出和无终结事件都映射为明确错误码。

取消可以使用独立的 stdin 控制消息：

```json
{"protocol_version":1,"request_id":"aq-001","command":"cancel"}
```

但不能只依赖 Python 自己响应取消。Rust 发送取消后等待有限时间；Worker 未退出时，Rust 必须终止进程并清理子进程树和 `.part` 文件。

### 15.5 AI 处理流水线

Python Worker 的内部流水线建议固定为：

```text
读取输入文件
    ↓
ffprobe/FFmpeg 探测并解码为 float32 PCM
    ↓
统一模型输入采样率、声道和幅度范围
    ↓
按窗口分块，窗口之间保留 overlap
    ↓
AI 模型推理
    ↓
overlap-add 拼接，避免分块边界突变
    ↓
检查 NaN/Inf、峰值和时长漂移
    ↓
写出 WAV 或 FLAC 无损中间文件
```

关键规则：

- AI Worker 的第一份输出优先是 WAV/FLAC，不要在 Python 推理后直接再次写低码率 MP3。
- 用户最终需要 MP3 时，由 Rust 侧已有 FFmpeg 能力从 AI 无损中间文件编码为 MP3；默认仍可生成 `曲目标题-艺术家.mp3`。
- 不随意将立体声转单声道；模型只支持单声道时，必须在任务详情中明确显示并允许用户取消。
- 模型要求 44.1 kHz 或 48 kHz 时，先高质量重采样到模型采样率；输出采样率策略必须记录，不能把升采样描述成恢复真实高频。
- 长音频必须分块处理，默认窗口 20 秒、重叠 2 秒仅作为起点，实际值由模型显存和边界伪影测试确定。
- 输出写盘前检查峰值、NaN/Inf、时长和声道数量；发现异常时任务失败，不把异常文件交给后续重命名。
- 除非用户显式选择，不对 AI 输出自动做响度归一化或限制器处理，避免把 AI 效果和音量变化混在一起。

### 15.6 模型路线和首期范围

“低质量”可能包括低码率、有噪声、削波、低采样率和混响，不能用一个模型解决所有问题。建议把模型能力拆成后端类型：

| 后端 | 目标 | 首期策略 |
|---|---|---|
| `music_bandwidth_extension` | 估计被低采样率/低码率削弱的频带 | 作为首个音乐 AI PoC |
| `speech_denoise` | 人声或讲话降噪 | 仅对语音输入开放，不默认用于音乐 |
| `declipping` | 修复峰值削波造成的失真 | 使用独立样本评估，默认关闭 |
| `dereverb` | 减少房间混响 | 后续评估，容易产生伪影 |

首个模型不应凭名称直接确定。建议用 5 类固定样本做小规模对比：低码率音乐、低采样率音乐、讲话、带底噪录音、削波录音。分别记录显存、CPU 时间、处理倍率、输出频谱变化、时长漂移、削波和人工盲听结果，再确定 `music-bandwidth-v1` 的实际模型来源和许可。

候选技术路线：

1. 优先评估可离线运行、可固定版本的 PyTorch/ONNX 模型。
2. 音乐带宽扩展可以评估 AudioSR 类模型，但要重点验证长音频分块和音乐伪影。
3. 语音降噪可以单独评估 DeepFilterNet 类模型，不将语音模型用于全部音乐下载。
4. 不把 Resemble Enhance、Demucs 等偏语音增强或分离模型直接当作通用音乐高保真模型，必须先用样本验证用途和效果。
5. 模型、权重和代码许可证在纳入应用前单独审查，记录来源、版本和 SHA-256。

首期只实现一个经过样本验收的模型后端，Worker 的协议和 Rust 编排层预留多模型扩展。没有可接受的模型效果时，宁可返回“模型不可用”，也不自动退回普通转码并显示为 AI 增强成功。

### 15.7 Rust 子进程启动和运行时解析

Rust 侧新增 `audio_quality::ai_worker`，集中负责 Worker 路径、Python 运行时和进程生命周期。建议路径优先级如下：

开发环境：

1. `AUDIO_AI_PYTHON` 环境变量指定的 Python 可执行文件。
2. 项目内 `.venv/Scripts/python.exe`。
3. 系统 PATH 中的 `python` 或 `python.exe`，只用于开发和诊断。

打包环境：

1. 随应用资源提供的 `audio-ai-worker.exe`（PyInstaller/Nuitka 等方式封装 Python 运行时）。
2. 若暂时不封装 Python，则使用资源目录内固定的 Python 嵌入式发行版和 `python.exe`，不依赖用户 PATH。
3. 模型目录来自应用数据目录或明确配置的资源目录，并通过 manifest 校验。

生产版不应假设用户已经安装 Python、PyTorch 或 CUDA。`audio_quality_check_ai_runtime` 命令需要在启动任务前返回：

```text
worker 是否存在、Python/Worker 版本、协议版本、模型是否存在、模型 hash 是否正确、CPU/GPU/运行时设备、可用显存或内存概况
```

当前 `src-tauri/tauri.conf.json` 只配置了 `fpcalc.exe` 和 `ffmpeg.exe` 资源。AI 方案落地时需要增加 Worker、Python 运行时依赖、模型 manifest 和模型权重的资源策略。模型权重是否随安装包分发，需要根据体积决定：小模型随包，大模型放在应用数据目录并由用户显式下载、校验和删除。

### 15.8 进程生命周期、取消和 Windows 安全

Rust 使用 `tokio::process::Command`，配置以下行为：

- `stdin`、`stdout`、`stderr` 使用 piped；设置 `PYTHONUNBUFFERED=1` 和 UTF-8 环境变量。
- 不经过 shell，不把用户文件路径拼成一条命令字符串。
- Windows 下隐藏 Worker 控制台窗口，避免每个任务弹出黑框。
- 记录 PID、启动时间、模型 ID 和运行时设备，但不把完整环境变量写入历史。
- 读取 stdout/stderr 使用异步任务，限制单条消息和累计日志大小。
- 任务取消时先发 JSON cancel，再等待短超时；超时后终止 Worker。
- Worker 可能再创建 FFmpeg、CUDA 或其他子进程，Windows 下需要使用 Job Object 或等价的进程树管理，确保取消不会留下孤儿进程。
- 子进程退出后必须 `wait`，确认退出码，再清理临时输出；不能只调用 kill 后立即认为任务结束。

错误码建议统一为：

```text
WORKER_NOT_FOUND
PROTOCOL_MISMATCH
MODEL_NOT_FOUND
MODEL_HASH_MISMATCH
UNSUPPORTED_INPUT
CUDA_UNAVAILABLE
OUT_OF_MEMORY
INFERENCE_FAILED
OUTPUT_INVALID
CANCELLED
WORKER_TIMEOUT
WORKER_EXITED
```

错误信息给用户看简短原因，stderr 尾部和完整诊断日志写入任务日志文件，避免把模型堆栈直接挤进前端卡片。

### 15.9 任务状态和 Tauri 接口扩展

原始音频识别和 Python AI 增强使用两组独立状态。`recognition_status` 只表示识别/自动命名，`quality_status` 只表示 Python AI 增强；未启用时分别为 `Disabled`。

识别字段沿用现有自动重命名规划：

recognition_result       标题、艺术家、置信度等结果

Python AI 字段如下：

建议命令：

| 命令 | 作用 |
|---|---|

| `audio_quality_probe` | 读取输入音频参数 |

### 15.10 与现有下载和自动重命名的最终顺序

两个开关独立生效，下载任务根据组合选择后处理路径。

两项都开启时，`AudioOnly` 任务顺序为：

```text
下载到 .m4a.part
    ↓
关闭文件并确认下载完成
    ↓
使用原始 .m4a 进行音频识别
    ↓
Rust 启动 Python AI Worker
    ↓
Worker 写出 .flac.part 或 .wav.part
    ↓
Rust 校验 AI 输出
    ↓
按用户目标格式编码；默认 MP3
    ↓
按识别结果生成“曲目标题-艺术家.mp3”
    ↓
更新任务、历史和前端事件
```

原因：音频识别使用原始下载文件最稳定，AI 可能改变频谱和指纹；先识别可以避免增强模型降低识别成功率。AI 处理失败时：

- 保留原始下载文件。
- 如果识别成功，仍可按识别结果将原始文件转为当前默认 MP3 并重命名，或按用户设置保留原始 M4A。
- `quality_status = Failed`，`recognition_status` 保留真实结果，不能把 AI 失败伪装成下载失败。
- 如果 AI 处理成功但最终 MP3 编码失败，保留经过校验的 FLAC/WAV master，等待用户重试编码。

下载配置使用两个独立开关：

```text
audioRecognitionEnabled        是否启用原始音频识别并自动重命名
pythonAiEnhancementEnabled     是否启用 Python AI 音频增强
recognitionConfidenceThreshold 识别置信度阈值
recognitionTemplate             默认 {title}-{artist}
pythonAiModelId                模型 ID
pythonAiDevice                 auto / cpu / cuda
pythonAiChunkSeconds           分块长度
pythonAiOverlapSeconds         分块重叠长度
pythonAiOutputFormat           wav / flac / mp3
keepAiMaster                   是否保留 AI 生成的 WAV/FLAC
keepOriginalAudio              是否保留原始下载文件，默认 true
```

四种组合的行为必须固定且可测试：

1. `false / false`：不调用识别服务，不启动 Python Worker；按原始标题输出。
2. `true / false`：只调用原始音频识别；识别成功后按 `曲目标题-艺术家` 命名。
3. `false / true`：只启动 Python Worker；AI 输出成功后按原始标题命名。
4. `true / true`：先识别原始文件，再启动 Python Worker；AI 输出成功后按识别结果命名。

这两个开关和最终输出格式仍然分开。FFmpeg 只作为解码、AI 输出后的格式编码以及失败回退能力，不等同于 Python AI 增强。旧版前端不传 AI 字段时，行为保持为现有“下载 → 识别/重命名 → MP3”流程。

### 15.11 分阶段实施计划

#### AI-1：Worker 协议和假 Worker

- 在不引入 PyTorch 的情况下先实现 Rust `tokio::process` 编排。

- 验证 Windows 中文路径、空格路径、长路径和特殊字符路径。

完成标志：Rust 可以稳定启动、通信、取消和回收 Python 子进程，测试不依赖 AI 模型。

#### AI-2：Python 推理最小闭环

- 新增独立 AI Python 包和 `requirements-ai.txt`。
- 先实现输入探测、短音频读取、固定模型加载和输出 WAV/FLAC。
- 仅支持单任务、CPU 或一种明确支持的 GPU 设备。
- 产出 `model_id`、版本、耗时、采样率、声道、时长和峰值信息。

完成标志：固定样本能完成“Rust → Python → AI 推理 → Rust 校验”，失败时原文件不受影响。

完成标志：长音频和批量任务可运行，取消不会留下 Worker、FFmpeg 或临时文件。

#### AI-4：独立前端页面

- 增加运行时检查、模型选择、CPU/GPU 选择、分块参数和保留源文件选项。

完成标志：不经过 B 站下载页面，用户可以独立完成 AI 音频增强。

完成标志：AI 后处理失败不影响已下载文件可用性，批量任务可以独立完成或失败。

### 15.12 AI 专项测试与验收

#### Rust Worker 测试

- fake Worker 正常完成、返回业务错误、输出非法 JSON、协议版本不一致、提前退出和无终结事件。
- stdout/stderr 并发读取不会死锁，日志超限会被截断。
- 取消后 Worker、FFmpeg 和其子进程均退出，临时文件被清理。
- Worker 启动超时、模型检查失败和退出码非零均得到确定错误码。
- 在 Windows 中文路径和包含空格的路径下输入输出正确。

#### Python Worker 测试

- 无模型、模型 hash 错误、输入格式不支持、采样率不支持和内存不足。
- 输入包含 NaN、极端峰值或超长时长时，Worker 不生成静默损坏文件。
- 分块拼接前后时长漂移在约定范围内，块边界没有明显突变。
- 输出无 NaN/Inf，声道数符合配置，采样率和文件格式符合 `result` 声明。
- 识别、推理和写出阶段的 stdout 始终保持纯 JSONL。

#### 音质效果验收

- 使用固定的无损母带生成低码率、低采样率和削波测试集，保留已知参考文件。
- 使用频谱、响度、峰值、时长、处理倍率等客观指标检查回归。
- 进行人工盲听 A/B，对音乐、人声、底噪和削波样本分别记录伪影。
- 不能只看输出文件码率、采样率或频谱高频增加来判定音质提升。
- 每个模型版本保存样本评估结果；模型升级需要重新跑固定测试集。

#### 下载集成验收

- `audioRecognitionEnabled = false` 时，不调用原始音频识别，文件名使用 B 站原始标题。
- `pythonAiEnhancementEnabled = false` 时，不启动 Python Worker，现有识别/重命名行为不变。
- 两项都开启时，顺序严格为原始音频识别、Python 推理、输出校验、最终编码和命名。
- 四种开关组合都必须有独立测试，不能只覆盖“两项都开启”。
- Python 失败、取消、超时或模型缺失时，原始文件仍可打开，历史中保存真实错误。
- AI 成功但最终 MP3 编码失败时，保留可验证的 FLAC/WAV master。
- 单个任务失败不会阻塞其他下载任务，AI 默认并发为 1。

### 15.13 更新后的总实施顺序

1. 保留现有 FFmpeg 模块作为探测、解码、最终编码和兜底能力，不把它当作 AI 音质恢复。
2. 先完成 Rust 与 fake Python Worker 的协议、取消和进程树测试。
3. 再加入真实 Python AI Worker 和一个经过样本评估的模型。
4. 独立页面跑通后，补模型资源管理、批量队列和历史记录。
5. 最后集成到 AudioOnly 下载，由两个独立开关决定是否执行原始识别和 Python AI。
6. 任何模型效果不达标时，保留原始文件并允许关闭 AI；不要用普通转码冒充 AI 处理结果。

### 15.14 GitHub 模型 PoC 记录

首个真实模型 PoC 使用 GitHub 上的
[`Rikorose/DeepFilterNet`](https://github.com/Rikorose/DeepFilterNet) 的
DeepFilterNet2 权重。仓库代码采用 MIT/Apache-2.0 双许可证，模型包为
`DeepFilterNet2.zip`，下载大小约 8.2 MiB；本地测试包 SHA-256 为
`850e695d1c27f2a7b4dcd89b16bc8d49367effc680b1369e995e31d46376cba7`。

该模型是 48 kHz 语音降噪模型，不是通用音乐音质恢复模型。因此它只用于
验证“Rust 启动 Python subprocess、加载本地权重、CPU 推理、写出音频和回传
结果”的真实闭环，不应在音乐下载任务中默认启用，也不能把语音降噪结果描述
为音乐无损修复。模型清单用 `backend=deepfilternet`、归档文件 SHA-256 和
解压后的运行目录进行校验；权重放在本地缓存，不提交到 Git。

音乐增强采用 AudioSR：其 GitHub 项目为
[`haoheliu/versatile_audio_super_resolution`](https://github.com/haoheliu/versatile_audio_super_resolution)，
代码采用 MIT 许可证，权重由 `audiosr` 从 Hugging Face 的
`haoheliu/audiosr_basic` 提供。AudioSR 是扩散模型，不符合 TorchScript 的直接
波形张量接口，因此通过独立 native Python backend 调用官方 API。

### 15.15 AudioSR 通用音乐恢复适配

模型清单登记 `audiosr-basic`，固定到 Hugging Face revision
`74a47f49061a1e788e968cc43ad45c0b6243f37d`。权重文件为
`models/cache/audiosr-basic/pytorch_model.bin`，大小必须为 `6,178,189,563`
bytes，SHA-256 必须为
`8a3506b9619ed32435ce2c115604750c7bddb5ad8502be7b1a3131bde878aa01`。
该文件约 5.75 GiB，不随仓库提交，也不会在下载音频或开始推理时自动下载。

AudioSR 0.0.7 的 `build_model()` 会忽略传入的 checkpoint 参数，直接调用内部
Hugging Face 下载函数。Worker 在模型文件通过大小和 SHA-256 校验后，仅在该次
模型加载期间将内部调用指向该本地路径，随后立即恢复原函数。这样可以继续采用
官方加载逻辑，同时保证推理阶段不会产生隐式网络访问；权重不存在、文件未完成
或哈希不匹配时，任务以明确错误结束。

为避免 5.75 GiB 文件的 SHA-256 计算阻塞 Worker 的 ready 握手，启动探测只校验
大于 128 MiB 的模型文件大小，并返回 `MODEL_HASH_DEFERRED` 状态。开始实际任务后
仍会在加载模型前完整计算 SHA-256，任何不匹配的权重都不会传给 AudioSR。

处理策略固定为 48 kHz：立体声文件按左右声道分别推理并在输出时复原声道数，
不会把音乐混为单声道。默认窗口为 10.24 秒、重叠 1.28 秒；Worker 对直接协议
请求的更大窗口也限制在 10.24 秒以内，因为官方实现明确提示更长输入会降低效果。
每个窗口先写入临时单声道 WAV，再调用 `super_resolution()`（50 DDIM steps），
裁掉模型内部补齐的尾部，最后使用 overlap-add 拼接。输出仍由 Worker 写为 WAV
或 FLAC，不能把重编码 MP3 作为 AI 恢复结果。

AI 依赖清单加入 `audiosr==0.0.7` 并固定 `numpy==1.23.5`，这是该版本 AudioSR
的兼容上限。模型代码为 MIT；模型权重的再分发许可需在实现显式安装器和打包前
单独确认，当前只支持用户下载并放置已校验的本地权重。

### 15.15.1 HiFi-GAN 神经声码器（音质优化）

除 AudioSR 超分辨率外，另提供 **HiFi-GAN 神经声码器**作为「音质优化」独立档位
（前端父菜单「音频品质提升」下与「音质提升」平级的「音质优化」视图）。其定位
与 AudioSR / FlashSR 不同，必须明确口径：

- **HiFi-GAN 是声码器（mel → waveform），不是超分辨率模型**。它只能重建 mel
  中**已包含**的频率内容，不能凭空补回丢失的高频。价值在于「神经波形重建」：
  把频谱表示重合成更干净、更少伪影的波形，提供不同于扩散系模型的「音色保真」
  档位，可作为 FlashSR / AudioSR 超分流水线的可切换 vocoder。
- 因此**不可**将其描述为「恢复高频 / 无损修复」；档位名统一用「音质优化 /
  保真重建 / 神经声码器」，沿用第 1 节口径。
- 处理策略固定 **48 kHz**：与 App 其它后端对齐。立体声按声道分别推理后合并
  （生成器为单声道）。默认整段前向（块可更大、重叠为 0），无需重叠相加。
- 复用 FlashSR 已 vendor 的 HiFi-GAN 实现与 `.venv-flashsr` 依赖，独立后端包
  `python/audio_ai_hifigan/`，协议与 `audio_ai_flashsr` 同构（`backend=hifigan`）。
- 权重策略待定（R3）：原生 48k 训练权重尚未锁定，manifest 条目 `hifigan-48k`
  的 `source` / `sha256` 为占位值，安装需待显式下载器落实真实权重与校验值；若
  仅能获得 22.05k 公开 checkpoint，则重建后重采样到 48k，并在档位说明标注
  「重建后重采样（非原生 48k）」。

### 15.16 Worker 异常退出诊断与本次实测结论

截图中的“AI Worker 进程异常退出，退出码: Some(1)”只包含 Rust 看到的进程
退出码，不能据此判断是 Python 解释器、依赖、模型、输入文件还是 FFmpeg 出错。
Rust 已统一读取 Worker 的 stderr；当 Worker 非零退出时，错误现在保留 stderr
末尾最多 8 KiB，空 stderr 时不追加空白诊断内容。这样前端任务详情可以直接显示
Python traceback 或运行时错误，超长日志不会无限占用内存。正常的 Python `error`
协议事件仍按机器可读错误码返回，不会被误判为进程崩溃。

排查顺序固定为：

1. 先执行 `audio_quality_check_ai_runtime`，确认 Worker 能发送 `ready`，并检查
   `models`、`model_errors` 和返回的实际 Python 路径。
2. 失败时保存错误文本中的 stderr 尾部，重点区分解释器/依赖、模型路径或 hash、
   输入解码、推理显存和 FFmpeg/ffprobe 路径。
3. 使用与应用相同的 `AUDIO_AI_PYTHON`、`AUDIO_AI_MODEL_DIR`、`AUDIO_AI_FFMPEG`
   和 `AUDIO_AI_FFPROBE` 环境变量复现，不用开发机 PATH 结果替代应用结果。
4. 确认输出文件存在后，再由 Rust 用 `ffprobe` 校验 FLAC、48 kHz、声道数和时长。

截至 2026-08-29，当前仓库环境已使用真实 `audiosr-basic` 权重完成 10.24 秒
立体声音频的 JSONL 端到端测试：`ready → load_model → inference → write_output →
result`，退出码为 0，输出为 48 kHz、2 声道、10.24 秒 FLAC。因此模型和 Python
依赖闭环已确认可用；若截图中的任务仍退出码为 1，应优先收集新版本错误中的 stderr，
并检查运行应用是否为打包版本。当前 Tauri 配置尚未随安装包提供 Python 运行时、
Worker 脚本和大模型权重，打包版资源策略仍是后续必须完成的工作，不能把开发机的
`CARGO_MANIFEST_DIR` 路径视为生产路径。
