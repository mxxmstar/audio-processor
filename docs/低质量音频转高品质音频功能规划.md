# 低质量音频转高品质音频功能规划

> 状态：规划中
> 编制日期：2026-08-24
> 目标：先实现一个可独立使用、可验证、不会破坏原文件的音频质量处理模块，再接入下载完成后的后处理流程。

## 1. 先明确“提升音质”的边界

低码率 MP3、AAC 等有损音频已经丢失了部分原始信息。把它重新编码为 320 kbps MP3、FLAC 或更高采样率，不会恢复这些细节，只会生成一个规格更高但信息量未增加的文件。因此产品和任务状态不能把普通转码显示为“无损恢复”。

本功能需要区分以下几类操作：

| 类型 | 能做什么 | 是否恢复丢失细节 | 首期建议 |
|---|---|---:|---|
| 无损重封装 | 在容器之间迁移音频流，不重新编码 | 否，但不引入二次损失 | 支持 |
| 普通转码 | 改变编码器、格式、码率或采样率 | 否，可能再次损失 | 支持 |
| 音频处理 | 音量标准化、限幅、轻度去噪、去削波等 | 改善部分听感，不保证恢复 | 谨慎支持 |
| AI 修复/超分 | 预测高频、去噪、去混响、去削波 | 只能估计，不保证真实还原 | 后续独立后端 |

首期产品名称建议使用“音频质量处理”或“音频增强”，并在详情中显示实际处理方式，例如“转码为 MP3 320 kbps”“已进行响度标准化”。对于有损输入，不显示“已恢复无损音质”。

## 2. 当前项目基础

项目已有可以复用的基础：

- `src-tauri/src/biliapi/media.rs` 已负责 FFmpeg 探测和进程调用。
- `media::transcode_audio` 已能将下载的音频转为 MP3，但参数固定为 `libmp3lame + -q:a 2`，不能表达完整的质量处理配置。
- `src-tauri/src/recognizer/` 已是与 Tauri 解耦的独立音频识别模块，可作为模块拆分和错误处理的参考。
- `src-tauri/src/biliapi/task.rs` 已有下载任务、临时文件和最终路径的概念。
- 前端使用 Vue 视图、Tauri command 和事件回传，适合新增独立的处理页面。

本功能不应直接扩大 `recognizer` 的职责。识别负责回答“这是什么音频”，质量处理负责回答“如何生成目标音频文件”，两者使用路径和结果交接即可。

## 3. 功能目标与非目标

### 3.1 首期目标

1. 选择一个或多个本地音频文件进行处理。
2. 处理前读取并展示输入音频的真实参数：格式、编码器、码率、采样率、声道、位深、时长和响度概况。
3. 提供明确的输出配置：输出格式、编码器、码率或质量、采样率、声道和响度处理。
4. 使用 FFmpeg 执行处理，支持进度、取消、失败状态和批量任务。
5. 输入文件默认不覆盖；输出写入同目录或用户指定目录的临时文件，成功校验后再原子移动。
6. 处理失败时保留原文件和错误信息，不能因为输出失败删除输入文件。
7. 对输出文件进行基本可播放性和参数校验，并记录实际使用的 FFmpeg 命令配置。
8. 为后续 AI 修复保留后端接口，但首期不捆绑大型模型或远程服务。

### 3.2 首期不包含

- 声称将 64/128 kbps 有损音频恢复为真正的 CD 级或母带级音质。
- 直接覆盖原文件。
- 首期内置 AI 模型下载、模型管理和 GPU 推理。
- 对视频文件做音轨替换或视频重新封装。
- 自动批量修改文件名和内部标签；命名仍由现有自动识别重命名流程负责。
- 以主观听感作为唯一验收标准。

## 4. 推荐处理档位

首期使用用户容易理解、但技术含义准确的档位。高级参数可以在“自定义”中展开。

### 4.1 保持源质量

适用于只需要转换容器或保留原编码的场景：

- 优先使用 `-c:a copy`，不重新编码。
- 当目标容器不兼容源编码时，明确提示会发生转码。
- 输出格式默认与源格式相容，不因为文件扩展名强行改变编码。

该档位不适合把低码率音频“变高质量”，但可以避免再次压缩。

### 4.2 高质量 MP3

适用于需要兼容性较好的 MP3 输出：

- 编码器：`libmp3lame`。
- 默认质量：VBR `-q:a 2`，与当前下载流程的默认行为保持一致。
- 可选固定码率：128、192、256、320 kbps。
- 默认不升采样；输出采样率跟随源文件，只有用户明确选择时才转换。

需要在界面上说明：选择 320 kbps 会得到高规格 MP3，不会恢复输入文件已经丢失的音频细节。

### 4.3 无损格式输出

适用于源文件本身为 WAV、FLAC、ALAC 等无损格式，或用户明确需要统一归档格式：

- 默认输出 FLAC。
- 源文件为有损格式时，显示“有损转 FLAC，仅改变容器/编码，不增加源文件信息量”的提示。
- 不把有损转 FLAC 的文件标记为“恢复无损”。

### 4.4 轻度音频处理

在自定义模式中按开关启用，并在任务详情中记录滤镜：

- 响度标准化：优先使用 `loudnorm`，显示目标 LUFS 和 true peak。
- 限幅：避免处理后峰值削波，必要时使用 `alimiter`。
- 轻度去噪：可评估 FFmpeg `afftdn`，默认关闭，避免音乐细节被误删。
- 去削波：可评估 `adeclip`，默认关闭，处理前后必须检查峰值和波形结果。
- 采样率转换：使用高质量 `soxr`，但不把升采样描述为增加频率细节。

首期不要默认串联过多滤镜。每增加一个滤镜，都应提供可回退的原文件、记录参数，并使用有代表性的音频样本进行听感和指标对比。

## 5. 独立模块设计

建议新增 `src-tauri/src/audio_quality/`，模块职责类似 `recognizer`，但只处理本地文件和 FFmpeg，不依赖 B 站任务。

### 5.1 推荐目录

```text
src-tauri/src/audio_quality/
├── mod.rs       对外 API、处理流程和类型导出
├── probe.rs     音频参数探测，优先使用 ffprobe
├── profile.rs   质量档位和输出配置
├── processor.rs FFmpeg 参数构造、启动、进度解析和结果校验
└── error.rs     可序列化的错误类型
```

若暂时没有 `ffprobe.exe`，可以先通过 FFmpeg 探测或限制首期展示字段；但建议随 `ffmpeg.exe` 一起提供匹配版本的 `ffprobe.exe`。不要通过解析人类可读的 FFmpeg 文本来作为长期数据接口，应优先使用 `ffprobe -of json`。

### 5.2 核心数据结构

建议使用稳定的 Rust 类型，Tauri 层只负责参数转换和事件转发：

```rust
pub struct AudioProbe {
    pub path: String,
    pub format: String,
    pub codec: String,
    pub duration_seconds: f64,
    pub bitrate: Option<u64>,
    pub sample_rate: Option<u32>,
    pub channels: Option<u16>,
    pub bit_depth: Option<u16>,
    pub lossless: bool,
    pub loudness: Option<LoudnessInfo>,
}

pub struct AudioQualityConfig {
    pub profile: QualityProfile,
    pub output_format: OutputFormat,
    pub bitrate_kbps: Option<u32>,
    pub sample_rate: Option<u32>,
    pub channels: ChannelMode,
    pub loudness: Option<LoudnessConfig>,
    pub denoise: bool,
    pub overwrite: bool,
}

pub enum ProcessingStatus {
    Pending,
    Probing,
    Processing,
    Verifying,
    Completed,
    Failed,
    Cancelled,
}

pub struct AudioProcessTask {
    pub id: String,
    pub input_path: String,
    pub output_path: Option<String>,
    pub input_probe: Option<AudioProbe>,
    pub output_probe: Option<AudioProbe>,
    pub config: AudioQualityConfig,
    pub status: ProcessingStatus,
    pub progress: f64,
    pub error: Option<String>,
}
```

实际实现可以按项目现有序列化方式调整，但应保留 `input_path`、`output_path`、输入/输出探测结果和配置快照，方便历史记录和问题排查。

### 5.3 对外 API

核心模块建议提供以下能力：

```text
probe(path) -> AudioProbe
validate_config(probe, config) -> Result<ValidatedConfig>
process(input, output, config, cancel, progress) -> Result<ProcessResult>
verify(output, expected_config) -> Result<AudioProbe>
```

`process` 不应负责选择文件、写历史或触发 Tauri command。它只接收输入路径、已分配的输出路径、配置和回调。这样可以在单元测试中使用 mock FFmpeg，也能在未来从下载任务直接调用，而不需要嵌套 `invoke`。

## 6. FFmpeg 执行与文件安全

### 6.1 处理流水线

```text
选择输入文件
    ↓
探测输入参数
    ↓
校验配置与输入兼容性
    ↓
在目标目录创建唯一的 .audio-processor-*.part
    ↓
启动 FFmpeg，解析进度并支持取消
    ↓
检查退出码、文件存在性、文件大小和输出参数
    ↓
原子移动到最终路径，写入任务/历史
```

FFmpeg 必须通过参数数组调用，不拼接 shell 字符串。输入、输出路径使用 `-i` 和最终参数传递，避免路径中空格、中文或特殊字符导致命令注入和解析错误。

### 6.2 临时文件和覆盖策略

- 临时文件与最终输出放在同一目录，尽可能保证移动是同一文件系统内的原子操作。
- 临时文件使用任务 ID，不使用未经清理的原始文件名。
- 默认不覆盖已存在的目标文件；同名时追加 `(1)`、`(2)`，复用现有 `audio_rename` 的冲突分配规则。
- 只有用户显式选择覆盖时才传递 `-y`，且仍先写临时文件，不能让 FFmpeg 直接破坏原目标。
- 成功移动后才删除临时文件和可选的原始文件；首期默认保留原始文件。
- 取消或失败时清理当前任务的临时输出，不触碰输入文件。

### 6.3 FFmpeg 进度

使用 `-progress pipe:1 -nostats` 输出机器可读进度，结合输入时长计算百分比。需要处理：

- 输入没有时长或时长为零：进度显示为“不确定”，不能伪造百分比。
- FFmpeg 输出错误在 stderr 中读取并截取可读尾部，避免把整个日志塞进任务状态。
- 取消时终止子进程并等待退出，避免残留 FFmpeg 进程锁住临时文件。
- 进度回调节流，避免每行 FFmpeg 输出都触发前端事件。

现有 `media::find_ffmpeg` 的探测逻辑应提取为公共能力复用；如果增加 `ffprobe`，探测路径和版本匹配规则也应集中管理。

## 7. Tauri 后端与前端

### 7.1 Tauri commands

建议新增独立命令模块，例如 `src-tauri/src/commands/audio_quality.rs`：

| 命令 | 作用 |
|---|---|
| `audio_quality_probe` | 探测一个或多个文件并返回输入参数 |
| `audio_quality_start` | 创建处理任务并立即返回任务 ID |
| `audio_quality_list_tasks` | 返回当前任务快照 |
| `audio_quality_cancel` | 取消指定任务 |
| `audio_quality_open_output` | 可选，打开输出文件或所在目录 |
| `audio_quality_clear_tasks` | 清理已结束的任务记录 |

处理在后台执行，前端通过 `audio-quality-progress` 事件接收：

```text
task_id、phase、status、percent、input_path、output_path、speed、error
```

阶段至少包括 `probe`、`process`、`verify`、`completed`。下载的 `download-progress` 事件继续只表达下载流程，避免两个模块共享一套含义不一致的状态。

### 7.2 前端独立页面

建议新增 `AudioQualityView.vue`，首期工作流为：

1. 选择本地音频文件。
2. 展示输入质量信息和文件大小。
3. 选择质量档位或自定义配置。
4. 预览输出格式、预计文件大小范围和“是否可能二次有损编码”的提示。
5. 启动、暂停/取消处理。
6. 展示每个任务的处理阶段、进度、输出文件和错误。
7. 处理完成后提供打开文件或打开目录操作。

首期不需要设计复杂的音频编辑器，也不需要展示无法可靠计算的“音质提升百分比”。如果输入是有损文件，应展示客观参数变化和免责声明，而不是虚构质量评分。

### 7.3 配置持久化

默认档位、输出目录、最后一次码率和响度目标可以写入现有应用配置；单个任务仍保存完整配置快照。配置版本需要保留，未来增加字段时使用默认值兼容旧任务。

## 8. 独立模块实施阶段

### 阶段 1：探测和纯本地配置层

- 确认并统一 `ffmpeg.exe`、`ffprobe.exe` 的开发期和打包期路径。
- 新增 `AudioProbe`、质量档位、输出格式和配置校验。
- 实现输入格式、码率、采样率、声道、时长的 JSON 探测。
- 实现文件名冲突、扩展名和临时路径分配。
- 不启动 Tauri，不接下载流程，先用固定样本测试。

完成标志：同一输入在不同配置下能得到稳定、可解释的校验结果，错误参数不会启动 FFmpeg。

### 阶段 2：FFmpeg 处理核心

- 实现保持源质量、高质量 MP3、FLAC 输出三个基础档位。
- 实现 `-progress` 进度解析、取消和错误映射。
- 实现临时文件、输出验证和原子移动。
- 添加轻度响度标准化的可选实现；默认关闭去噪等可能改变音色的滤镜。
- 为每种输出保存实际配置和探测结果。

完成标志：输入文件始终保留，成功任务输出可播放且参数符合配置，失败任务无半成品冒充成功。

### 阶段 3：Tauri 命令和独立页面

- 注册 command 和 `audio-quality-progress` 事件。
- 新增任务状态管理和并发限制。
- 完成文件选择、参数设置、批量处理、取消、打开输出。
- 增加历史记录或至少提供任务详情导出，确保重启前能查到输出路径和错误。

完成标志：不经过 B 站下载页面，用户可以直接处理本地音频并完成端到端验收。

### 阶段 4：试听和质量评估

- 使用 WAV、FLAC、AAC、MP3 的固定样本覆盖无损和多种有损输入。
- 记录输入/输出 codec、码率、采样率、响度、true peak 和削波计数。
- 对去噪、限幅、响度标准化样本进行人工试听，记录误伤细节的情况。
- 建立“只改变格式”“改变音量”“改变频谱”的测试样本，避免把不同问题混在一起。

完成标志：每个档位都有清晰的收益、代价和适用输入，不以单一文件的听感作为普遍结论。

## 9. 与下载流程的集成阶段

独立模块稳定后，再接入 `AudioOnly` 下载。推荐集成顺序如下：

```text
下载到 .m4a.part
    ↓
关闭文件并检查完整性
    ↓
用原始下载文件执行音频识别
    ↓
根据用户设置执行音频质量处理
    ↓
校验处理结果
    ↓
按识别出的“曲目标题-艺术家”分配最终文件名
    ↓
更新任务状态、实际路径和下载历史
```

识别应放在质量处理之前，原因是处理滤镜、重采样或 AI 增强可能改变指纹，使用原始下载文件更有利于保持识别成功率。质量处理失败时，仍保留原始下载文件并按现有识别重命名逻辑兜底。

### 9.1 下载配置扩展

在现有下载输入中增加可选的质量处理配置：

```text
audioQualityEnabled       是否在 AudioOnly 完成后处理
audioQualityProfile       source / mp3-high / flac / custom
audioQualityConfig        自定义码率、采样率、响度和滤镜
keepOriginalAudio         是否保留原始下载文件，默认 true
```

兼容规则：旧版前端不传这些字段时，保持当前下载行为；自动识别重命名和音频质量处理分别有独立开关和状态。视频、仅视频和合并模式首期不进入该处理链路。

### 9.2 任务状态

不要把“处理中”直接覆盖下载传输状态。可在现有 `DownloadTask` 增加独立字段，例如：

```text
quality_status       Disabled / Pending / Processing / Completed / Failed / Cancelled
quality_config       本次实际使用的配置
quality_input_path   处理输入路径
quality_output_path  处理输出路径
quality_probe        输入/输出参数摘要
quality_error        处理错误
```

下载成功但质量处理失败时，下载任务仍为 `Completed`，质量状态为 `Failed`，并将原始文件路径作为可操作输出。这样用户不会因为后处理失败而误以为下载内容丢失。

### 9.3 推荐的文件保留策略

默认保留原始音频：

```text
原始下载：<目录>/.audio-processor-<id>.m4a.part
处理临时：<目录>/.audio-processor-<id>.mp3.part
最终增强：<目录>/曲目标题-艺术家.mp3
原始归档：<目录>/曲目标题-艺术家.source.m4a
```

实际命名可以简化，但必须保证：

- 质量处理成功前不删除 `.m4a`。
- 用户选择保留原文件时，原文件必须有明确的 `.source` 或独立子目录。
- 不允许输出文件和输入文件路径相同后直接覆盖。
- 下载历史同时保存原始输入路径、处理输出路径和最终用户可见路径。

首期如果不想增加用户可见的原始副本，可以保留隐藏源文件并在任务详情中提供“保留原始文件”设置；无论 UI 如何呈现，失败回退路径必须存在。

## 10. AI 修复/超分的后续方案

AI 能力应作为 `audio_quality` 的另一种处理后端，而不是修改现有 FFmpeg 参数来冒充 AI：

```text
AudioQualityBackend
├── FfmpegBackend       转码、重采样、响度、轻度滤镜
└── AiEnhancementBackend 去噪、去混响、频带扩展、去削波
```

AI 后端需要单独解决：

- 模型文件体积、版本、许可证和校验值。
- CPU/GPU 推理能力探测和显存/内存占用。
- 长音频分段、重叠窗口、拼接边界和延迟。
- 输入输出采样率、声道和模型支持范围。
- 取消任务时安全终止推理，避免残留进程。
- 效果不可逆，必须保留源文件和增强前后对比试听能力。
- 不同音乐类型可能出现伪影，必须允许关闭和回退。

AI 后端完成前，产品只应提供“转码”“重采样”“响度处理”等准确描述。评估 AI 时，可以先以独立命令行原型验证样本效果，再决定是否将模型随应用分发。

## 11. 测试计划

### 11.1 单元测试

- `AudioQualityConfig` 的默认值、边界值和互斥配置校验。
- 输入路径、输出路径、扩展名和同名文件分配。
- MP3、FLAC、AAC、WAV 探测 JSON 的正常和缺字段情况。
- FFmpeg 进度行解析、无时长输入、异常退出和取消状态。
- 临时文件清理、输出不存在、输出为空和原子移动失败。
- 有损输入转 FLAC 时状态和提示文案不错误宣称恢复音质。

### 11.2 集成测试

- 使用项目内固定短音频或本地生成测试音频，不能依赖 B 站和外网。
- 验证 MP3 320 kbps、VBR、FLAC 和源流复制的实际 codec 与参数。
- 验证响度处理前后 LUFS/true peak 变化在目标范围内。
- 验证取消后 FFmpeg 子进程退出且无残留 `.part`。
- 验证输出失败时原文件仍可播放，任务状态为 `Failed`。
- 验证批量任务中单个失败不会阻塞其他任务。

### 11.3 下载集成测试

- 下载完成后先识别原始文件，再进入质量处理。
- 关闭质量处理时，现有自动识别重命名行为完全不变。
- 质量处理失败时保留原始文件并正确写入历史。
- 识别失败和质量处理失败同时发生时，两种错误状态都可见。
- 暂停、停止和断点续传不会误触发质量处理。
- 重复下载不会覆盖源文件或已存在的最终文件。

### 11.4 手工验收

- 在开发环境和打包环境分别验证 `ffmpeg.exe`/`ffprobe.exe` 路径。
- 使用真实的低码率人声、音乐、带削波音频试听处理前后差异。
- 检查中文、日文、特殊字符和长路径下的输入输出。
- 检查任务详情、历史记录、打开文件和错误信息是否指向实际最终路径。

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 高码率输出被误解为音质恢复 | UI 和任务详情显示真实处理类型，不使用“恢复无损”表述 |
| 再次有损编码造成更多损失 | 默认提供源流复制/FLAC 选项，明确提示二次编码 |
| 升采样只增加采样点 | 默认跟随源采样率，使用高质量重采样且不虚构收益 |
| 去噪/限幅损伤音乐细节 | 默认关闭高风险滤镜，逐项开关，保留原文件 |
| FFmpeg/ffprobe 版本或路径不一致 | 集中探测、启动时记录版本，打包时放入匹配资源 |
| 输出中途失败留下假成功文件 | `.part` + 退出码/参数/可播放性校验 + 原子移动 |
| 批量任务占满 CPU/磁盘 | 独立处理并发配置，默认并发 1 或 2，限制队列 |
| AI 模型产生伪影或资源占用过高 | AI 单独后端、可关闭、保留源文件并限制模型范围 |

## 13. 验收标准

- [ ] 可以从独立页面选择本地音频并完成探测、处理和输出。
- [ ] 用户可以区分源流复制、普通转码、响度处理和 AI 增强。
- [ ] 普通转码不会被描述为恢复已丢失的音频细节。
- [ ] 任务展示真实输入/输出参数、处理配置、进度和错误。
- [ ] 处理失败、取消或应用异常时，输入文件不会被删除或覆盖。
- [ ] 输出经过退出码、文件存在性和参数探测校验后才标记成功。
- [ ] 批量任务支持独立失败和并发限制。
- [ ] 下载集成时顺序为“原始文件识别 → 质量处理 → 文件命名”，且后处理失败可回退。
- [ ] 历史记录保存实际输出路径和质量处理配置。
- [ ] `cargo test`、`cargo check`、`cargo check --examples`、`npm run build` 通过；自动化测试不依赖外网。

## 14. 建议实施顺序

1. 先实现 `audio_quality` 的类型、探测、配置校验和纯本地路径分配。
2. 再实现 FFmpeg 处理、进度、取消、验证和原子移动。
3. 独立页面端到端跑通本地文件处理后，再补批量并发和历史。
4. 用固定样本完成客观指标和人工试听验收。
5. 最后把处理配置接入 `AudioOnly` 下载，保持识别重命名链路向后兼容。
6. AI 修复作为独立后端做原型评估，效果和资源可接受后再产品化。
