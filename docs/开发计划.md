# audio-processor 开发计划（B 站解析 / 下载能力）

> 本文档基于 `src-tauri/src/http_client/说明文档.md` 与 `src-tauri/src/biliapi/README.md` 的待办章节整理，
> 将"复现 bilidownload 的 B 站解析 + 下载能力"拆分为可落地的阶段，并详细列出每个阶段需要实现的功能。
>
> 基线（已完成，无需重复）：
> - `http_client` P0/P1 已全部修复：模块注册、统一 reqwest、Mozilla UA、`no_proxy()`、WBI 签名（md5 crate）。
> - `biliapi` 已封装：视频/番剧/收藏夹/合集/热门信息、`get_play_info`、扫码登录、WBI key 24h 内存缓存。
> - `biliapi::stream` 已实现：按 Codecid 优先级挑视频直链、FLAC 优先挑音频直链。
> - 全部测试通过（`cargo test --lib biliapi` 9 passed，`http_client` 4 passed）。

## 阶段 1：解析能力完善

> 目标：让调用方能一次性拿到"一个视频 / 一个合集 / 一部番剧"的全部可用直链，而不只是单分集。

### 1.1 清晰度与编码枚举补全（`biliapi::types`） ✅ 已完成
- [ ] 在 `MediaFormat` 基础上补充"编码偏好"枚举（`Codecid`：AV1/H264/HEVC），并暴露 `stream::codecid` 常量。
- [ ] 提供"清晰度降级链"辅助：如 `[1080P+, 1080P, 720P, 360P]`，供 `get_streams` 在目标清晰度无流时自动回退重试。

### 1.2 单视频完整解析流程（`biliapi::video`） ✅ 已完成
- [ ] 新增 `resolve_video(client, bvid, prefer_format) -> ResolveResult`：
  1. 调 `get_video_info` 拿 `pages`（多 P）；
  2. 对每个 `page.cid` 调 `get_streams`；
  3. 目标清晰度失败则按降级链重试，记录实际选用清晰度；
  4. 返回 `Vec<StreamSelection>`（每 P 一组音视频直链）+ 视频元信息。
- [ ] `ResolveResult` 结构含：`title`、`pages: Vec<PageStream>`，`PageStream { page, part, video_url, audio_url, actual_format }`。

### 1.3 合集批量解析（`biliapi::video`） ✅ 已完成
- [ ] `resolve_collection(client, mid, season_id)`：复用 `get_seasons_archives_first_bvid` 思路，扩展为"拉全部分集列表"。
- [ ] 当前 `seasons_archives_list` 接口需翻页（Go 版用 `page_num`/`page_size`），补齐分页遍历逻辑，聚合所有 `bvid`。
- [ ] 对每个 `bvid` 调用阶段 1.2 的 `resolve_video`，合并为 `Vec<ResolveResult>`。

### 1.4 番剧/影视批量解析（`biliapi::video`） ✅ 已完成
- [ ] `resolve_season(client, ssid/epid)`：复用 `get_season_info`，遍历 `episodes[]`（含 `bvid`/`cid`）。
- [ ] 每个 `episode` 直接构造 `get_play_info` + `stream::select_streams`（番剧单集通常单 cid，无需多 P 遍历）。
- [ ] 处理"需大会员/付费"的 `code`（-404/-412 等），在 `BiliApiError` 中给出可读原因而非裸错误。

### 1.5 单元测试 ✅ 已完成
- [ ] 用假 JSON 构造 `VideoInfo`（多 pages）、`SeasonInfo`（多 episodes），验证 `resolve_*` 聚合逻辑与降级链行为（参考 `stream.rs` 现有测试风格）。

**阶段 1 完成标志**：给定一个 bvid / 合集 id / 番剧 id，能返回结构化、带实际清晰度的音视频直链清单。

## 阶段 2：下载能力（http_client 流式）

> 目标：让 `http_client` 能"边下边写"几 MB~几 GB 的音视频直链，而非全量读入内存。
> 对应 Go 版 `DownloadMedia`（`io.TeeReader` 边下边写磁盘 + 进度 + 重试）。

### 2.1 流式下载方法（`http_client::client`） ✅ 已完成
- [ ] 启用 `reqwest` 的 `stream` feature。
- [ ] 新增 `async fn download_to_file(&self, url, path, on_progress)`：
  - 用 `response.bytes_stream()` + `tokio::io::copy` 写入文件；
  - `on_progress(downloaded: u64, total: Option<u64>)` 回调（total 来自 `Content-Length`）；
  - 支持 `Range` 断点续传（可选，先实现基础版）。
- [ ] 直链通常需带 `Referer`/`User-Agent`，复用 `BiliClient` 默认头或新增 `download_with_config`。

### 2.2 重试机制（`http_client`） ✅ 已完成
- [ ] `RequestConfig` 增加 `retry: u32`（默认 0）；`send()` 与 `download_to_file` 用循环包裹，指数退避。
- [ ] 区分"可重试"（超时、5xx、连接断开）与"不可重试"（4xx 业务错误）。

### 2.3 进度回调标准化 ✅ 已完成
- [ ] 定义 `Progress` 结构：`{ downloaded, total, speed, percent }`；
- [ ] 在下载方法内按固定时间间隔（如 200ms）节流触发回调，避免刷屏。

### 2.4 响应 Cookie 读取（补 5.1-4） ✅ 已完成
- [ ] `HttpResponse` 增加 `cookies: Vec<(String,String)>`（迭代 `response.cookies()`），供登录态提取 `SESSDATA`。
- [ ] 进度/完成回调补全错误字段（`CallbackInfo.error: Option<String>`）。

### 2.5 单测 / 集成测试
- [ ] 用本地文件服务器或 `wiremock` 验证流式写入正确性、进度回调触发次数、重试生效。
- [ ] 删除 `client.rs` 中写死内网地址 `192.168.66.83` 的调试测试（见说明文档 4.12）。

**阶段 2 完成标志**：一条直链可下载为本地文件，带进度、可重试，不撑爆内存。

## 阶段 3：音视频下载编排

> 目标：把"直链"变成"本地文件"，支持音频-only / 视频-only / 音视频合并三种模式，并支持并发任务。

### 3.1 任务模型（`biliapi` 或新模块 `task`） ✅ 已完成
- [ ] 定义 `DownloadTask { id, title, video_url, audio_url, mode, output_path, status, progress }`。
- [ ] `mode` 枚举：`AudioOnly` / `VideoOnly` / `Merge`（对应 Go 版 download 模式）。

### 3.2 下载执行 ✅ 已完成
- [ ] `AudioOnly`：仅下载 `audio_url` → `<title>.m4a/.aac`。
- [ ] `VideoOnly`：仅下载 `video_url` → `<title>.mp4`。
- [ ] `Merge`：分别下载音/视频到临时文件，再用 `ffmpeg` 合并为 `<title>.mp4`（复用项目已有 `ffmpeg`/`bin` 或系统 PATH）。
  - 检查 ffmpeg 可用性，缺失时回退为仅下载音/视频并给出提示。

### 3.3 并发与队列 ✅ 已完成
- [ ] 简单并发池（如 `tokio::task` + `Semaphore` 限制 N 路并发，对齐 Go 版并发控制）。
- [ ] 单个任务失败不影响整体；记录失败原因，支持"重试失败项"。

### 3.4 关联阶段 1 ✅ 已完成
- [ ] 批量解析结果（`Vec<ResolveResult>`）可直接展开为多个 `DownloadTask`，形成"解析 → 下载"流水线。

**阶段 3 完成标志**：从 bvid 到本地 mp4/m4a 全链路跑通，可批量、可并发、可合并。

## 依赖关系与建议执行顺序

```
阶段1（解析完善） ─┐
                   ├─→ 阶段3（下载编排） ─→ 阶段5（UI）
阶段2（流式下载） ─┘
阶段4（登录/存储） ─┘（可与 1/2 并行）
```

- 阶段 1 与阶段 2 相互独立，可并行推进；
- 阶段 3 必须等 1、2 完成；
- 阶段 4 可独立并行，建议尽早做（登录态是高频痛点）；
- 阶段 5 放最后，依赖前四阶段稳定。
